# 부채 분류 체계와 품질 기준선 — 기술 부채 프레임워크 응용

> 🌐 **[Read in English](../en/13-debt-and-quality-bar.md)**

**버전**: 1.0.1
**콘텐츠 해시**: sha256:79b7dfe5b59b (본문 기준, 이 두 줄 제외)

"나중에 고치자"고 미룬 것들이 얼마나 쌓여있는지 추적하지 않으면, 프로젝트는
계속 커지는데 실제 신뢰도는 그대로거나 떨어지는 걸 아무도 모르게 된다. 이
크리스탈은 **부채를 종류별로 분류하는 법**과 **서비스가 실사용 가능한지
판정하는 최소 품질 기준선**을 정리한다.

## 1. 부채 분류 — Fowler/McConnell 사분면 응용

## 근거 (1차 자료 확인)

🟢 Martin Fowler, "TechnicalDebtQuadrant" 원문 확인(martinfowler.com/bliki) —
Steve McConnell이 처음 구분한 두 축을 그대로 인용한다: **무모함(reckless)
vs 신중함(prudent)**(단기 이익이 명확한가) × **의도적(deliberate) vs
비의도적(inadvertent)**(팀이 의식적으로 선택했는가).

| | 의도적(Deliberate) | 비의도적(Inadvertent) |
|---|---|---|
| **무모함(Reckless)** | "품질 신경 안 쓰고 빨리 간다" — 장기 비용을 과소평가한 채 알고도 지름길을 택함 | 설계 관행을 몰라서 생기는 지저분한 코드 — 팀이 부채가 쌓이는 줄도 모름 |
| **신중함(Prudent)** | "지금은 이렇게 가고 나중에 갚는다" — 출시 기한을 맞추려 의식적으로 지름길을 택하고 상환 계획도 있음 | 1년간 실제로 만들어보고서야 "이렇게 설계했어야 했다"는 걸 깨닫는 것 — 뛰어난 팀에도 불가피하게 발생, 예상해야 함 |

**AI 에이전트 프로젝트 적용**: "검증 케이스 없이 일단 배포"는 무모-의도적
부채(상환 계획이 있으면 신중-의도적로 격상 가능), "판정 로직에 숨은 편향이
있는 줄 몰랐다"는 비의도적 부채(무모/신중 여부는 사후에 그 편향을 얼마나
빨리 잡아낼 체계가 있었는지로 판가름난다).

## 2. 표준 부채 마커 — 5단계

| 마커 | 뜻 |
|---|---|
| ✅ 공식통과 | 정해진 검증 절차(평가 케이스 등)를 실제로 통과했다 |
| 🟢 실행완료 | 실제로 실행해서 결과를 냈지만, 공식 검증 절차는 아직 안 거쳤다 |
| 🟠 부분검증 | 일부만 확인했다(전수가 아니라 표본 등) |
| ⚪ 미실행 | 아직 한 번도 실제로 돌려본 적 없다(설계만 있음) |
| 해당없음 | 이 항목 자체가 이 대상에 적용되지 않는다 |

**부채율 계산**: `✅ 공식통과`가 아닌 항목의 비율. 이 비율이
[05-autonomous-agent-operating-principles.md](05-autonomous-agent-operating-principles.md)의
"우선순위를 정하는 법" 1~2번 단계(부채가 임계치 이상이면 검증을 새 작업보다
우선한다)를 구동하는 입력값이다.

## 3. 서비스 품질 기준선 — 최소 5기준

부채와는 다른 축이다(부채=검증 여부, 이건=**실제로 상용 서비스 수준인가**):

| # | 기준 | 확인 방법 |
|---|---|---|
| 1 | **입력 검증**: 예상 밖 입력(빈 값, 형식 오류, 극단값)에 크래시하지 않는다 | 의도적으로 이상 입력을 넣어 테스트 |
| 2 | **실패 처리**: 실패했을 때 조용히 빈 결과를 내지 않고, 명확한 에러/원인을 남긴다 | 의도적으로 의존 자원을 끊고 실행 |
| 3 | **비용 통제**: 실행 비용(토큰/API 호출/시간)에 상한이 있거나, 최소한 실측·로그가 남는다 | 실행 로그에서 비용 필드 확인 |
| 4 | **재현 가능성**: 같은 입력에 결과가 매번 크게 달라지지 않는다(완전한 결정론은 아니어도, 핵심 판단은 안정적이다) | 같은 입력을 여러 번 실행해 결과 분산 확인 |
| 5 | **관측가능성**: 실행 결과가 "잘 됐다"는 주장이 아니라 검증 가능한 로그로 남는다 | [11-observability-and-agent-tracing.md](11-observability-and-agent-tracing.md) 참고 |

## 4. 두 축을 같이 쓰는 법

```
        검증됐는가(부채)          상용 수준인가(품질기준선)
"완성"   = ✅ 공식통과           +  5기준 전부 충족
"동작함"  = 🟢 실행완료           +  5기준 일부만 충족(어디가 부족한지 명시)
"위험"   = ⚪ 미실행 또는 검증 없이 자동 반복 실행 중
```

두 축을 하나로 뭉뚱그리면 "검증은 됐는데 실은 크래시가 잦다"거나 "안정적인데
검증 케이스가 없다" 같은 서로 다른 문제를 구분 못 한다.

## 5. 부채 상환 우선순위를 정하는 법

부채가 발견됐다고 전부 즉시 갚지 않는다 — [05-autonomous-agent-operating-principles.md](05-autonomous-agent-operating-principles.md)의
"최종 수혜자는 사용자다" 원칙과 연결: 내부 진단 도구가 만든 "검증 필요"
목록은 그 자체로 자동 실행 대상 큐가 아니다. 상환 우선순위는:

1. **신중-의도적 부채**(상환 계획이 있던 것)를 먼저 — 계획대로 갚는 것 자체가
   신뢰를 쌓는다.
2. **[12-blameless-postmortem-template.md](12-blameless-postmortem-template.md)에서
   "2회 재현" 판정을 받은 것** — 우연이 아니라 패턴으로 확인된 것.
3. 나머지는 부채율이 임계치를 넘었을 때만 체계적으로 처리한다.
