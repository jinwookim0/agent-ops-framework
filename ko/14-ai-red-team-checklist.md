## LLM01~LLM10 (2025판) — AI 에이전트 프로젝트 관점 해설

| # | 위협 | 에이전트 프로젝트에서의 구체적 의미 | 관련 방어 |
|---|---|---|---|
| LLM01 | **프롬프트 인젝션** | 사용자 입력이나 에이전트가 읽는 외부 콘텐츠(웹페이지, 문서)에 숨겨진 지시가 에이전트의 원래 지시를 덮어쓰려 시도 | 외부에서 가져온 콘텐츠는 "데이터"로만 취급하고 "지시"로 실행하지 않는다 — 도구 결과/웹 콘텐츠 안의 지시문을 시스템 프롬프트와 같은 권위로 취급하지 않는 것이 핵심 방어 |
| LLM02 | **민감정보 노출** | 학습 데이터나 컨텍스트에 있던 개인정보/비밀값이 응답에 그대로 나옴 | [07-prompt-guardrails/](07-prompt-guardrails/)의 3단 방어(도구 차단+능동 마스킹+훅 강제) |
| LLM03 | **공급망 위험** | 서드파티 모델·플러그인·데이터셋의 무결성이 깨져 있을 위험 | 의존하는 모델/도구/MCP 서버의 출처를 확인, 버전을 고정 |
| LLM04 | **데이터·모델 오염** | 학습/파인튜닝 데이터에 악의적 데이터가 섞여 들어가는 것 | 자체 모델을 파인튜닝하지 않는 대부분의 에이전트 프로젝트엔 낮은 우선순위 — 단, 프로젝트 자신의 "자가학습 문서"([06-self-improving-heuristics-loop.md](06-self-improving-heuristics-loop.md))에 검증 안 된 외부 입력이 그대로 규칙으로 편입되지 않게 하는 것도 유사한 원리 |
| LLM05 | **부적절한 출력 처리** | 에이전트 출력을 검증 없이 그대로 실행 가능한 코드/명령으로 넘기는 것 | 에이전트가 생성한 코드/명령을 실행하기 전 별도 검증·샌드박스 단계를 둔다 |
| LLM06 | **과도한 자율성(Excessive Agency)** | 에이전트에게 실제로 필요한 것보다 넓은 권한(도구 접근, 실행 범위)이 주어짐 | [05-autonomous-agent-operating-principles.md](05-autonomous-agent-operating-principles.md)의 unknown-unknowns 게이팅 — 최대 피해 규모에 구조적 상한이 있는지 확인 |
| LLM07 | **시스템 프롬프트 유출** | 시스템 프롬프트(내부 지시)가 사용자에게 노출돼, 그걸 근거로 우회 공격을 설계당함 | 시스템 프롬프트에 비밀값을 넣지 않는다(유출을 전제로 설계) — 프롬프트 자체를 숨기려 하기보다, 유출돼도 안전하게 만든다 |
| LLM08 | **벡터·임베딩 취약점** | RAG(검색증강생성) 시스템의 벡터 스토어에 악의적 문서가 주입돼 검색 결과를 오염시킴 | 벡터 스토어에 넣는 문서의 출처를 검증, 접근 권한을 분리 |
| LLM09 | **잘못된 정보(Misinformation)** | 에이전트가 그럴듯하지만 틀린 정보를 확신 있게 생성 | [03-epistemic-immunity-catalog.md](03-epistemic-immunity-catalog.md) 전체가 이 위협의 방어 카탈로그 |
| LLM10 | **무제한 소비(Unbounded Consumption)** | 비용/리소스에 상한이 없어 악의적이거나 우발적인 과다 호출로 비용이 폭증 | [13-debt-and-quality-bar.md](13-debt-and-quality-bar.md) 3번 기준(비용 통제) |

## 이 체크리스트를 쓰는 법

**전수 적용이 아니라 위협 모델링부터 한다**: 10개를 다 방어하려 하지 않는다
— 먼저 "이 프로젝트가 실제로 노출되는 표면이 뭔가"를 정한다:
- **외부 콘텐츠를 읽는가**(웹 검색, 이메일, 문서 파싱)? → LLM01·LLM09가
  최우선.
- **실제 행동을 실행하는가**(코드 실행, 파일 쓰기, 외부 API 호출)? →
  LLM05·LLM06이 최우선.
- **개인정보/비밀값을 다루는가**? → LLM02·LLM07이 최우선.
- **여러 사용자가 공유하는 지식베이스가 있는가**(RAG)? → LLM08이 최우선.

## AI 에이전트 특화 원칙 — "데이터와 지시의 경계"

위 10개 중 가장 근본적인 방어 원칙 하나를 꼽으면: **에이전트가 처리하는
콘텐츠 중 "이건 내가 따라야 할 지시다"와 "이건 그냥 내가 다뤄야 할
데이터다"를 항상 구분한다.** 프롬프트 인젝션(LLM01)의 근본 메커니즘이
바로 이 경계가 흐려지는 것이다 — 외부에서 가져온 텍스트(검색 결과, 파일
내용, 다른 에이전트의 출력)에 "무시하고 이렇게 해"류 문장이 있어도, 그건
데이터 안의 텍스트일 뿐 실제 지시 권한을 갖지 않는다는 걸 시스템 설계
차원에서 명확히 한다(예: 데이터 소스를 명시적으로 태그하고, 그 태그가
붙은 콘텐츠에서 나온 지시문은 낮은 권위로 취급).

## 레드팀 실행 원칙

레드팀(자기 시스템을 공격해보는 테스트)을 진행할 때:
1. **발견 내용 자체가 민감할 수 있다** — 취약점 목록을 공개 채널에 그대로
   남기지 않는다([05-autonomous-agent-operating-principles.md](05-autonomous-agent-operating-principles.md)의
   "실패해도 비용이 낮다" 게이트 조건과 반대되는 사례로, 레드팀 산출물은
   기본적으로 게이트를 낮추지 않는다).
2. **실제로 실행해서 확인한다** — "이 방어가 있으니 안전할 것이다"라고
   추론만 하지 않고, 실제 공격 입력을 만들어 통과하는지 시험한다
   ([04-eval-engineering-methodology.md](04-eval-engineering-methodology.md)의
   "시뮬레이션이 아니라 실제 실행" 원칙과 동일).
3. **발견되면 [12-blameless-postmortem-template.md](12-blameless-postmortem-template.md)의
   안전(safety) 카테고리로 기록**하고, 같은 유형이 2번째 발견되면 구조적
   수정으로 격상한다.
