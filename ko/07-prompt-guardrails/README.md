## 왜 4단인가 — 각 단이 막는 실패 모드가 다르다

| 단계 | 언제 작동하는가 | 막는 것 | 한계 |
|---|---|---|---|
| **1차. 도구 차단** (`settings.json`) | 파일을 **읽으려는 시도 자체** | 민감 경로가 애초에 컨텍스트(프롬프트)에 들어오는 것 | 컨텍스트에 이미 들어온 뒤에는 못 막음 |
| **2차. 능동 마스킹** (`scripts/mask-sensitive-output.py`) | 사람(AI)이 명령을 **직접 실행**했을 때 | 이미 컨텍스트에 있는 내용 중 패턴 매칭되는 것을 실제로 치환 | 실행을 잊으면 작동 안 함 — 그래서 3차가 필요 |
| **3차. 훅 강제** (`hooks/guard-secrets.sh`) | 발행/커밋 **도구 호출 직전, 자동**(Claude Code의 Bash 도구 호출 경계 안에서만) | 2차를 사람이 깜빡해도, 도구 호출 자체를 가로채 자동으로 검사·차단 | Claude Code를 거치지 않고 사람이 터미널에서 직접 `git push`하면 이 훅 자체가 아예 안 뜬다 |
| **4차. 네이티브 git pre-push 훅** (`hooks/pre-push-verify.sh`) | `git push`가 **실제로 원격에 나가기 직전**, git 자체가 호출(Claude Code와 무관) | 3차가 못 보는 경로(사람이 직접 push) + 커밋 메시지 자체에 섞여든 값(파일 내용과는 다른 채널) | `core.hooksPath` 설정을 잊으면 조용히 작동 안 함(아래 "설치" 5번); `--no-verify`로 항상 우회 가능 — 강제가 아니라 안전망 |

네 단계는 서로 다른 실패 모드를 막는다 — 하나만 있으면 안 되고 넷을 같이
둬야 방어선이 완성된다.

## 설치

1. `settings.json`의 `permissions.deny` 목록에서 `shared/local/**`을 이
   프로젝트가 실제로 로컬 전용 민감 파일을 두는 디렉터리 이름으로 바꾼다.
   나머지(`.env`, SSH/AWS 키)는 대부분 프로젝트에 그대로 적용된다.
2. `hooks/guard-secrets.sh`의 `Artifact` matcher를, 이 프로젝트가 실제로
   쓰는 외부 발행/배포 도구 이름으로 바꾼다(여러 개면 훅을 여러 개 등록하거나
   matcher를 파이프로 나열).
3. 세 파일(`settings.json`→`.claude/settings.json`, `hooks/guard-secrets.sh`
   →`.claude/hooks/guard-secrets.sh`, `scripts/*.py`·`scripts/*.sh`→
   `scripts/`)을 대상 프로젝트의 같은 상대 경로에 복사한다 — `settings.json`의
   `command` 필드가 `${CLAUDE_PROJECT_DIR}/.claude/hooks/guard-secrets.sh`를
   가리키므로 경로를 그대로 유지하는 게 가장 간단하다.
4. 설치 직후 반드시 라이브로 검증한다 — 민감 패턴이 든 더미 파일을 만들어
   실제로 발행/커밋을 시도해보고, 차단 메시지가 실제로 뜨는지 확인한다
   (주장이 아니라 로그로 확인하는 것 — [03-epistemic-immunity-catalog.md](../03-epistemic-immunity-catalog.md)
   8번 항목과 같은 원칙). 확인 후 더미 파일은 지운다.
5. 4차(네이티브 git pre-push 훅)까지 쓰려면 `hooks/pre-push-verify.sh`를
   그대로 복사한 뒤, `.githooks/pre-push`가 그 파일을 가리키게 하고
   `git config core.hooksPath .githooks`를 실행한다 — `.git/hooks/`는
   git이 버전관리하지 않아 클론마다 따로 설정해야 하므로, 이 설정 자체를
   `CONTRIBUTING.md`의 "처음 클론했을 때 할 일"에 적어두는 걸 권한다.

## 검증 상태

원본은 실제 프로젝트에서 다음을 라이브로 확인했다: (1) 시크릿 패턴이 든
파일로 발행을 시도해 훅이 실제로 차단(`exit 2`, 도구 호출 자체가 거부됨),
(2) 클린 파일은 오탐 없이 통과, (3) 매칭 안 되는 도구 이름은 훅이 즉시
통과(`exit 0`). 이 검증은 **원본 프로젝트에서 한 것**이지 이 크리스탈
버전을 다른 프로젝트에 설치한 뒤 재검증한 게 아니다 — 설치 후 4단계
안내대로 반드시 라이브 재검증한다(`module-format.md`의 "검증 표시는
정직하게" 원칙과 동일).

써야 하는 것 아닌가"라는 질문에서 시작)**: 3차(`guard-secrets.sh`)는

pre-push-verify.sh`(네이티브 git pre-push 훅)를 4차로 추가해 이 경로를
닫았다. 이 훅은 (a) 지금 push되는 커밋들의 **메시지 자체**를 스캔해서
세션 링크·로컬 절대경로·PEM 키 패턴이 섞였는지 확인하고(파일 내용이

다시 확인한다(같은 패턴을 또 베끼지 않고 재사용). 실제로 이번 세션
자체에서, 완전히 다른 이유로 이미 이런 종류의 문제(모든 커밋 메시지에
세션 링크가 들어간 것)를 겪고 나서야 이 빈틈이 드러났다 — G1(실제
사고 근거)을 그대로 충족하는 사례다.

**FIX됨(2026-09-01, 위 pre-push 훅을 직접 테스트하다가 발견 — 이번
세션에서 가장 심각한 발견)**: `public-repo-check.sh`(ko/en 둘 다)가
패턴 검사에 `grep -InE`를 써왔는데, 대문자 `-I`는 "바이너리 파일
무시" 옵션이지 대소문자 무시(`-i`, 소문자)가 아니다 — 즉 이 스크립트는
공개된 이후 계속 **대소문자를 구분해서** 시크릿 키 패턴을 검사하고
있었다. 라이브로 재현: `API_KEY=abcd1234567890xyz`가 든 파일을 만들어
돌려보면 exit 0(클린)이 나왔다 — 형제 스크립트 `mask-sensitive-
output.py`는 같은 패턴에 `re.IGNORECASE`를 명시해서 정상적으로 잡는데
(exit 1 확인), 바로 그 형제 스크립트가 이미 겪어서 고쳐둔 문제를 이
파일만 놓치고 있었던 것 — "두 파일이 같은 탐지 목록을 독립적으로
유지하므로 한쪽만 고치고 잊으면 방어에 구멍이 생긴다"는 이 문서
자신의 "확장하는 법" 절이 정확히 경고하는 그 실패 모드가 오탈자
하나로 실제로 일어난 사례다. `-inE`(소문자)로 수정하고 실제로
`API_KEY=...` 테스트를 다시 돌려 exit 1로 바뀐 것, 그리고 이 저장소
전체를 다시 스캔해도 새 오탐이 없는 것까지 확인했다. 새로 만든
`pre-push-verify.sh`도 커밋 메시지 검사에 같은 오타를 그대로 베껴
써서 함께 고쳤다 — "Claude-Session:"이 대문자로 시작하는데 정작 이
훅의 패턴은 소문자였다면, 방금 4차로 추가한 방어 자체가 처음부터
무력했을 것이다.

**DOCUMENT만 함(구조적 한계라 완전 해소 불가능, 아래처럼 알고 쓸 것)**:
- **정규식 탐지의 근본 한계**: 이메일을 "골뱅이"로 풀어쓰거나 유니코드
  유사자형으로 바꾸면 안 걸린다. GCP/Azure 자격증명, `scheme://
  user:pass@host` 형태의 연결 문자열, 영어가 아닌 시크릿 레이블은
  여전히 못 잡는다 — 벤더 형식을 전부 따라잡는 건 끝나지 않는 경쟁이라
  완전한 목록을 목표로 하지 않는다.
- **`guard-secrets.sh`의 git 훅 범위는 이름보다 좁다**: `git commit`/
  `git push`라는 **리터럴 문자열**만 매칭한다 — 같은 Bash 도구 호출
  안에서도 `curl`/`scp`/`npm publish`/`docker push`나 별칭(alias)으로
  우회한 git 호출은 전혀 스캔하지 않는다. "도구 호출 경계 밖은 못
  본다"는 기존 문구는 이 범위 자체가 좁다는 걸 별도로 밝히지 않았었다.
- **콘텐츠 해시는 자기일관성 검사이지 변조 방지가 아니다**: 스탬핑
  도구가 공개돼 있어, 내용을 실제로 고친 사람이 스탬프도 같이 다시
  찍으면 해시는 "일치"로 나온다 — "버전을 깜빡하고 안 올린 경우"는
  잡지만 "의도적으로 도구까지 써서 재스탬프한 경우"는 못 잡는다.
- **번역 동기화(DIVERGED) 신호는 재스탬프 한 번으로 초기화된다**:
  `agent-ops-framework-translation-sync-check.py`는 스탬프 값이 마지막
  으로 바뀐 시점만 추적해서, 재번역 없이 스탬프만 새로 찍으면 신호가
  사라진다 — 이것도 체크섬과 서명의 차이와 같은 근본적 한계다.
- **git 히스토리 재작성에 취약했던 문제 — 2026-09-01 근본 재설계로 해소**:
  이 항목은 원래 "구조적 한계라 완전 해소 불가능"으로 분류돼 있었지만,
  실제로 해소됐으므로 정정한다. 경위: 한 세션 안에서 두 차례 squash를
  거치며 `translated-from` 스탬프 44개 중 37개가 도달 불가능한(orphan)
  커밋을 가리키게 된 게 실제로 발견됐다 — `git log -1 --format=%ct <해시>`가
  아직 gc되지 않은 dangling 커밋에도 "성공"해 조용히 통과하는 바람에
  로컬에서는 한동안 티가 안 났다. **1차 대응**(`git merge-base
  --is-ancestor` 기반 도달가능성 검사 + `--repair` 옵션)은 감지·복구를
  자동화했을 뿐, 히스토리 재작성 자체가 여전히 위험하다는 근본 문제는
  남겨뒀다 — "재작성할 때마다 사람이 `--repair`를 기억해서 실행해야
  한다"는 건 이 폴더 자신이 다른 곳에서 이미 비판하는 바로 그 패턴이다
  (문서화된 규칙은 실행을 잊으면 무력하다 — 이 README 맨 위 "왜 4단인가"
  절의 2차/3차 구분과 같은 교훈). **근본 수정**: `translated-from` 스탬프를
  git 커밋 해시가 아니라 **콘텐츠 해시**(SSOT 본문의 sha256 + 번역본
  자기 본문의 sha256, 둘 다 `agent-ops-framework-version-check.py`가
  ko/ 크리스탈 자기 일관성에 이미 쓰던 것과 같은 방식)로 통째로 재설계해,
  git 객체를 아예 참조하지 않게 만들었다 — squash/rebase/force-push
  무엇을 해도 콘텐츠 해시는 깨질 수 없다. 같은 squash를 스크래치 클론에서
  재현해 실제로 검증: 재설계 전엔 37/44가 깨졌던 동일한 조작이, 재설계
  후엔 0/44 — 이론이 아니라 라이브로 확인됨. 자세한 내용은
  `scripts/agent-ops-framework-translation-sync-check.py`의 "Why
  content-hash, not commit-hash" 절 참고.
- **live 배포판과 이 템플릿 사이 드리프트**: 실제 배포된 `.claude/
  hooks/guard-secrets.sh`는 이 템플릿에 없는 대외비 경로 차단 로직
  (confidential-paths.txt/pending-human-review-paths.txt)을 추가로
  갖고 있다 — 이 폴더를 통째로 복사해 새 프로젝트에 이식하면 그
  기능은 안 따라온다는 뜻이다.

이 목록 자체가 이 코드를 못 믿을 이유가 아니라, "무엇을 확인했고 무엇을
아직 못 했는지"를 정직하게 표시하는 것이 이 프레임워크 전체의 원칙이라
여기도 똑같이 적용한 것이다.

## 확장하는 법

`PATTERNS`(mask-sensitive-output.py)와 `check(...)` 호출(public-repo-check.sh)에
같은 정규식을 각각 추가해야 한다 — 두 파일이 같은 탐지 목록을 독립적으로
유지하므로, 한쪽만 고치고 잊으면 방어에 구멍이 생긴다(파일 상단 주석에
이미 이 경고가 적혀 있다). 프로젝트별로 흔한 패턴(예: 사내 시스템의 특정
토큰 형식)이 있으면 같은 방식으로 추가한다.
