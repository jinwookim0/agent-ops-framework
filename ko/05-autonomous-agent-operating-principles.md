Problems in AI Safety(Amodei 2016) 등 공개 논문과 Anthropic 공식 에이전트
가이드의 핵심 주장을 원문 대조했고, 정지/계속 판단 규칙은 원본 프로젝트의

프로젝트를 사람이 매번 다음 지시를 주지 않아도 AI 에이전트가 스스로 다음
행동을 판단해 계속 진행하게 하려면(자동 모드/자율 루프), "언제 멈추고 언제
계속할지"를 명시적으로 정의해야 한다. 이 문서는 그 판단 규칙을 정리한다.

## 0번째 원칙 — 절대 깨지 않는 것

자율성의 범위가 아무리 넓어져도, 다음 세 가지는 **절대 자율 판단의 대상이
아니다**:

1. **보안**: 비밀키·자격증명·프라이버시 스캔을 매 커밋/발행 전 실행하고,
   절대 우회하지 않는다.
2. **프라이버시**: 실제 개인정보(정확한 소득·가족구성·건강정보 등)를
   지어내거나 유출하지 않는다.
3. **신뢰성**: 지어낸 사실을 검증된 것처럼 말하지 않는다("확인 필요" 정직
   표기), 비가역적 행동(결제·실제 발신 등 되돌리기 어려운 것)은 여전히
   먼저 묻는다 — 이건 "느려서"가 아니라 절대선이라 자율성 확장 대상이 아니다.

이 세 가지 밖의 영역(어떤 기능을 얼마나 깊게 팔지, 언제 무엇을 만들지 같은
판단)에서는 매번 확인을 기다리지 않고 진행하되, 판단 근거는 계속 정직하게
기록한다(투명성은 자율성의 대가다).

## 정지 트리거를 "행동 위험"뿐 아니라 "인식론적 신호"로도 확장한다

0번째 원칙과 위 두 절은 **행동의 비가역성**을 기준으로 언제 멈출지 정한다.
하지만 장시간 실행되는 작업에는 다른 종류의 위험이 있다 — 행동 자체는
안전(파일 쓰기, 읽기 전용 조사)한데, **내용이 조용히 원래 목표에서
벗어나거나, 검증되지 않은 주장을 사실처럼 계속 쌓아가는 것**이다. 이건
행동 위험이 아니라 **인식론적(epistemic) 위험**이고, 같은 "정지" 메커니즘을
다른 트리거 조건으로 확장해서 다룬다.

**구체적 트리거 신호(예시, 완전한 목록 아님)** — 아래 중 하나라도 걸리면
다음 행동을 계속하기 전에 명시적으로 멈춰 재점검한다:
- 여러 차례 연속으로 도구 호출을 했는데, 그중 어느 것도 지금 만들고 있는
  주장을 직접 뒷받침하는 확인 가능한 결과로 이어지지 않았다(주장 옆에
  실제 로그를 붙인다는 [11-observability-and-agent-tracing.md](11-observability-and-agent-tracing.md)의 원칙이 지켜지고 있는지 자체 점검).
- 지금 하고 있는 일이 이 작업을 시작할 때 명시했던 목표·계획과 실제로
  다른 방향으로 여러 단계 흘러갔다(계획 자체가 바뀌었으면 그 변경을 명시,
  그냥 흘러간 것이면 되돌아간다).
- 사실 확인이 필요한 주장인데 외부 검증(검색·조회) 없이 내부 추론만으로
  답을 만들고 있다.

**정지 후 무엇을 하는가**: 자기비평(self-critique)만으로 재점검하는 것과,
외부 근거를 다시 확보(재검색·재조회)하는 것은 효과가 다르다 — Self-Refine
(Madaan et al. 2023, [arXiv:2303.17651](https://arxiv.org/abs/2303.17651))
원문이 실측한 바로는, 같은 모델이 스스로 비평·수정하는 루프가 정답이
열려있는 과제에서는 크게 개선되지만, **모델이 이미 강할수록 자기비평만의
개선폭이 급격히 줄어들고(약한 모델 +4.8점 vs 강한 모델 +0.7점, 5점 만점
척도)**, 정답이 하나뿐인 과제에서는 거의 효과가 없었다(93점→93점,
그 모델은 94%의 경우 "이미 다 좋다"고만 답함). 반면 검색 기반 외부 근거
결합(RAG, Lewis et al. 2020, [arXiv:2005.11401](https://arxiv.org/abs/2005.11401))은
사실성 평가에서 검색 없는 순수 생성보다 크게 선호됐다(42.7% vs 7.1%).
**결론**: 가능하면 정지 후 재점검을 "다시 한번 생각해보기"로 끝내지 않고
"실제로 다시 조회해서 근거를 갱신하기"로 만든다 — 자기비평은 근거가 없을
때의 차선책이지 첫 번째 선택지가 아니다.

**이게 03·04와 다른 지점**: [03-epistemic-immunity-catalog.md](03-epistemic-immunity-catalog.md)는 이미 벌어진 추론 오류의 **유형 사전**이고,
[04-eval-engineering-methodology.md](04-eval-engineering-methodology.md)는
**완결된 산출물**을 평가한다 — 둘 다 사후 또는 배치 시점에 쓰인다. 이 절은
그 대신 **아직 실행 중인 작업 도중** 같은 신호가 나타났을 때 계속 진행하기
전에 멈추는 것에 관한 것이다. 트리거 조건은 다르지만, 실제 "멈춘다"는
행동 자체는 이 문서의 다른 정지 메커니즘(0번째 원칙)을 그대로 재사용한다.

## 게이트를 낮춰도(자동화를 강화해도) 되는 기준 — Unknown Unknowns 매트릭스

"안다는 것을 아는 것(known-known) / 안다는 것을 모르는 것(known-unknown) /
모른다는 것도 모르는 것(unknown-unknown)" 3단계 구분(도널드 럼즈펠드가
대중화한 리스크 분류 프레임)을 자동화 게이트 판단에 적용한다.

**핵심 통찰**: unknown-unknown(모른다는 것도 모르는 위험)은 확률로 추정할
수 없다 — 정의상 예측 불가능하기 때문이다. 하지만 **행동의 구조적 성질이
"최대 피해 규모(blast radius)에 상한이 있는가"는 확률과 무관하게 판단할 수
있다.** 예: 버전관리로 추적되는 로컬 파일 쓰기는 무슨 일이 일어나든 되돌릴
수 있다 — 이 상한은 "그런 사고가 일어날 확률"과 무관하게 항상 성립한다.
반면 실제 이메일 발신은 무슨 안전장치를 걸어도 되돌릴 방법이 구조적으로
없다.

**게이트를 낮춰도 되는 조건 — 4가지 전부 충족해야 함**:

| # | 조건 | 판정 방법 |
|---|---|---|
| 1 | **알려진 위험(Known)이 낮다** | 이 행동의 비가역 요소가 없거나, 있어도 영향이 국소적(이 프로젝트 안에서만) |
| 2 | **알려진-모름(Known-unknown) 위험도 낮다** | 이 행동이 실패하는 그럴듯한 시나리오를 상상했을 때, 실패해도 비용이 낮다 |
| 3 | **모른다는 것도 모르는(Unknown-unknown) 위험에 구조적 상한이 있다** | 확률 추정이 아니라 구조로 증명: (a) 버전관리로 추적돼 되돌리기 가능한가, (b) 플랫폼 자체의 안전장치(예: 기본 비공개, 충돌 감지)가 있는가, (c) 제3자·외부 시스템·실물 자원(돈/건강/법률)에 닿지 않는가 — 셋 중 하나라도 "아니오"면 상한이 없다고 본다 |
| 4 | **실제 운영에서 이미 그 수준으로 다뤄지고 있다** | 문서상 게이트와 실제 관행이 어긋나 있다면, 문서를 실제에 맞추는 것이지 새 리스크를 도입하는 게 아니다 |

**중요한 자기검증 경계**: 조건 4의 "지금까지 N번 무사고였다"는 track record는
그 자체로 통계적 안전성의 근거가 아니다 — 실패율 5%를 95% 확신으로
배제하려면 필요한 최소 시행 횟수는 생각보다 크다(수십 회 단위). 게이트를
낮추는 결정이 여전히 유효하다면 그건 조건 3의 **구조적** 상한 논거(표본
크기와 무관하게 항상 성립) 덕분이지, track record가 통계적으로 충분해서가
아니다 — 두 근거를 섞어 말하지 않는다.

**적용 예시**:
- 발행 도구가 "기본 비공개, 발행 충돌 시 자동 거부"라는 플랫폼 안전장치를
  가지면, 최악의 경우도 "본인만 보는 잘못된 비공개 페이지"에 그친다 →
  게이트를 낮출 수 있다.
- 실제 이메일 발신은 외부 수신함에 닿고, 보낸 뒤 되돌릴 구조적 방법이
  없다(조건 3의 (c) 위반) → 게이트를 유지한다.
- 레드팀/보안 감사 성격의 작업은 발견 내용 자체가 민감할 수 있어 "실패해도
  비용이 낮다"(조건 2)를 항상 만족한다고 보기 어렵다 → 게이트를 유지한다.

## 우선순위를 정하는 법 (임의로 고르지 않는다)

매 반복(iteration)마다 이 순서로 다음 할 일을 정한다:

1. **부채(검증 안 된 기존 작업의 비율)를 계산한다** — 표준 마커(공식통과/
   실행완료/부분검증/미실행/해당없음) 기준.
2. **부채가 임계치(예: 50%) 이상이면 검증을 새 작업보다 우선한다** — 단,
   부채가 높아도 실제로 가치 있다고 판단되는 확장을 완전히 밀어내지는
   않는다(균형).
3. **부채가 임계치 미만이면** 미해결 백로그 중 하나를 처리한다.
4. **그것도 없으면 다양성 확장**: 여러 실행이 쌓이는 작업에 "다양성 커버리지"
   표가 있으면, **빈 셀이 가장 많은 축**을 채우는 대상을 고른다 — 임의로
   아무거나 고르지 않는다.
5. **그것도 없으면**: 상태를 갱신하고 다음 신호를 기다린다(억지로 새 작업을
   만들어내지 않는다 — 절제 원칙).

매 반복 후 실행 요약을 로그에 남긴다(비용 관측 원칙 유지).

## 최종 수혜자는 사용자다 — 내부 도구 검증은 자기목적화되지 않는다

AI가 스스로 만든 진단 도구가 찾아낸 "재검증 필요" 목록은 그 자체로 자율
실행 대상 큐가 아니다. 부채가 이미 낮은 상태에서 이런 목록을 계속
소진해나가는 건, 이미 통과 마커가 붙어있는 항목을 더 확실하게 만드는 일이지
사용자가 실제로 체감할 결과물을 만드는 일이 아니다. **원칙**: (1) 내부
진단 목록은 사용자가 명시적으로 요청하거나 공식 부채가 임계치 이상일 때만
자동으로 소진한다 — 그 외엔 신호로만 기록하고 자동 실행하지 않는다. (2)
반복이 쌓일수록 "눈에 보이는, 완성된, 공유 가능한" 중간 산출물을 의식적으로
우선한다 — 검증 로그·근본원인 기록은 계속 정직하게 남기되, 그것만으로 한
반복을 채우지 않는다.

## 대화 턴 안에서도 멈추지 않는다

"요청 하나 끝내면 보고하고 대기"하는 관례는 자동 모드(백그라운드 반복)에만
적용되기 쉽다 — 사람과 실시간으로 대화하는 턴 안에서도 같은 원칙을 적용한다.
명시적으로 사용자 입력이 필요한 지점(개인정보, 확인이 필요한 되돌리기 어려운
행동)이 아니면, 완료 보고 뒤 곧바로 다음으로 가치 있는 행동을 스스로 골라
이어간다 — 매번 "이제 뭘 할까요?"라고 멈추지 않는다. 백그라운드 작업의 완료
알림 도착 자체도 같은 "계속 진행" 트리거로 취급한다.

**멈추는 게 정당한 경우는 정확히 3가지뿐이다**: ①사람 확인이 필요한 되돌리기
어려운 행동(0번째 원칙), ②쿼터/비용/부채 임계 초과, ③사용자의 명시적 정지
지시. 이 셋이 아닌데 "충분히 많이 했으니 확인받자"는 식으로 요약 직후 멈추는
건 암묵적 정지이지 정당한 정지가 아니다.

### 문서화된 규칙만으로는 재발을 못 막는다 — 자기재예약 백스톱이 진짜 수정이다

"곧바로 다음 행동을 잇는다"는 규칙을 문서에 적어두는 것과, 실제로 매번 그렇게
하는 것 사이엔 간극이 있다 — **같은 근본 원인(암묵적 정지)이 여러 번 재발하고
나서야 이 간극이 드러난다**는 게 반복 관측된 패턴이다. 원인은 "규칙은
있었지만 그걸 강제하는 메커니즘이 없었다"는 것 — 이건 이 문서·이 폴더 다른
크리스탈들이 공유하는 "문서화만으론 재발을 못 막는다"는 교훈이 이 절 자신에게
적용된 사례이기도 하다.

**구조적 수정**: 정지가 정당한 3가지 경우가 아니면, 턴을 마치기 전에 **자기
자신을 다시 깨우는 예약을 실제로 건다**(예: 다음 iteration을 스스로 예약하는
메커니즘, 그 iteration 종료 시 다시 스스로를 예약하는 반복 체인) — "충분히
했다"는 자체 판단을 신뢰하지 않고, 외부 예약 메커니즘이 안전망으로 남게
한다. 선택적으로 같은 간격의 독립된 백업 트리거를 하나 더 걸어(있다면), 한
메커니즘이 실패해도 다른 하나가 남도록 한다.

### 예약 간격은 관측된 변화 속도에 맞춰 스스로 조정한다

예약 간격을 아무리 짧게 잡아도 "재개까지의 최대 지연"만 줄지, "그 주기마다
새로운 개선이 일어남"을 보장하지 않는다 — **진짜 속도 레버는 간격이 아니라
턴 안에서 다음 행동을 계속 잇는 것**이고, 이 재예약은 "정말 할 일이 없다고
판단해 턴을 끝냈을 때"의 안전망일 뿐 주된 메커니즘이 아니다. 안전망 자체도
낭비될 수 있다: 재예약이 여러 차례 연속으로 "확인했지만 상태 변화 없음"만
반환하면, 그 간격이 실제 변화 속도보다 짧다는 신호다 — 간격을 늘린다. 늘린
뒤에도 계속 변화가 없으면, 무한 폴링을 유지하는 대신 **재예약 자체를 멈춘다**
— 안전망의 목적은 진행 중이던 작업을 놓치지 않는 것이지 정적 상태를 영원히
지켜보는 게 아니다. 새로운 실제 신호(사람과의 새 상호작용 등)가 들어오면 그
시점에 다시 무장한다.

## 병행 실행 주체 간 충돌 방지 (예: cron + CI가 동시에 같은 저장소에 쓸 때)

프로젝트에 두 개 이상의 독립된 자동 실행 주체가 같은 공유 저장소에 커밋할
수 있으면, "나 혼자 쓰는 유일한 주체"라는 전제가 깨진다. 모든 자동 push는
다음 절차를 따른다:

```bash
git add -A && git commit -F <메시지파일>
for i in 1 2 3; do
  git push origin main && break
  git pull --rebase origin main   # 상대가 먼저 넣은 커밋 위로 재정렬
done
```

- **`--force`/`--force-with-lease`는 이 상황에서 절대 쓰지 않는다** — 다른
  자동 실행 주체의 실제 작업을 지울 수 있다.
- 재시도에도 실패하면 강제로 뚫지 않고 "push 충돌, 수동 확인 필요"로
  기록하고 그 반복은 종료한다.

## 언제·무엇을 탐구할지 정하는 능력 (상위 판단)

기계적 우선순위 규칙만으로는 못 잡는 더 상위의 판단이 있다 — 언제 규칙을
따르고 언제 규칙 밖의 고leverage 선택을 할지:

1. **한 갈래를 얼마나 파고들지 스스로 판단한다** — 무한정 반복하지도, 한
   번 해보고 포기하지도 않는다.
2. **막힘(병목)을 만나면 우회로를 찾지, 같은 방식을 반복하지 않는다.**
3. **다음 질문 자체를 스스로 만든다** — 주어진 목록을 순서대로 처리하는
   게 아니라, 지금까지의 결과가 다음에 무엇을 물어야 하는지를 알려준다.
4. **깊이 파는 것과 종합해서 내보이는 것 사이에서 전환 시점을 안다** —
   더 파고들 수 있어도, 그게 항상 다음으로 가장 가치 있는 행동은 아니다.

이 네 가지는 매번 기계적으로 적용할 체크리스트가 아니라, 각 순간에 실제로
다시 물어야 하는 질문들이다.

## 실행상 한계 (과장하지 않기 위해 미리 밝힌다)

- 예약 실행(cron 등)이 세션/프로세스에 종속된 방식이면, "노트북을 꺼도
  영원히 돌아가는 자동화"가 아니다 — 세션이 살아있는 동안만 작동한다는 걸
  정확히 부르고 과장하지 않는다.
- "판정 근거를 문서에 적어두는 것"만으로는 실제 반복이 보장되지 않는다 —
  중요한 반복 루틴은 매 판단 사이클의 체크리스트에 명시적으로 박아넣어야
  한다(문서화와 실제 실행 사이의 간극은 반복적으로 발생하는 실패 패턴이다).
