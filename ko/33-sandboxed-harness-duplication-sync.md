# 샌드박스 실행기의 중복 하네스 — import가 안 될 때 정직하게 중복하고 기계적으로 대조한다

따르고, 이를 강제하는 대조 스크립트가 실전 배치되어 반복 사용된 걸 직접
확인 — 단, 이건 외부 표준과의 대조가 아니라 이 프로젝트 자신의 운영
이력을 직접 연 확인이다(BLUEPRINT.md 1절의 근거 경로 (a)). 이 패턴이 다른
샌드박스 실행 환경·다른 팀에서도 똑같이 통하는지는 별도로 확인되지 않았다.

## 문제

일부 에이전트 실행 환경(워크플로 스크립트, 플러그인 샌드박스 등)은
로컬 모듈을 `import`하는 걸 허용하지 않는다 — 매 실행이 독립된 파일
하나로 완결돼야 한다. 그런데 검증된 로직(예: 채점 함수, 판정 스키마)을
여러 실행 파일이 똑같이 써야 하는 경우는 흔하다. "그냥 복사해서 쓰면
되지"라고 넘기면, 원본을 고친 뒤 복사본들을 깜빡하고 안 고치는 드리프트가
반드시 발생한다 — 사람이 "나중에 다 같이 고쳐야지"라고 기억에만
의존하는 건 이 프레임워크가 반복적으로 겪은 실패 패턴([05-autonomous-
agent-operating-principles.md](05-autonomous-agent-operating-principles.md)의
"문서화만으론 재발을 못 막는다"와 같은 계보)이다.

## 해법 — 정직한 중복 + 기계적 대조

1. **정본(canonical)은 하나만 둔다**: 단위 테스트가 가능한 별도 라이브러리
   파일에 로직을 한 번만 작성하고 검증한다.
2. **호출부마다 손으로 복사한다**: import가 안 되니 각 실행 파일에
   정본의 내용을 그대로 붙여넣는다 — 이건 임시방편이 아니라 **이
   환경 제약 안에서 유일하게 동작하는 정직한 선택**이다. 참조로 연결하는
   척하지 않는다.
3. **복사본과 정본을 기계적으로 대조하는 스크립트를 만든다**: 공백을
   정리한 뒤 각 복사본을 정본과 diff한다 — 사람이 기억해서 대조하는 게
   아니라 커밋 시점(또는 정기 점검 시점)에 스크립트가 드리프트를
   구조적으로 잡아낸다. "복사했다"는 주석 하나로 신뢰를 대체하지 않는다.

이 3단계가 갖춰지면, "로직은 한 곳에서만 검증되고 테스트되지만 실행은
제약 때문에 여러 곳에 물리적으로 존재한다"는 모순이 **드리프트 없이**
유지된다.

## 부가 이점 — 매개변수화된 하네스

같은 종류의 실행(예: A와 B를 비교 판정하는 실험)이 반복되면, 정본
자체를 "고정 골격 + 교체 가능한 페이로드"로 나눈다 — 새 비교 종류를
추가할 때 골격 코드를 새로 안 만들고 페이로드(무엇을 비교할지, 판정
스키마)만 바꿔 끼운다. 골격이 한 곳(정본)에서만 검증되므로, 새 비교
유형을 추가해도 매번 처음부터 재검증할 필요가 없다.

## 이 패턴이 적용되는 조건

- 실행 환경이 로컬 모듈 import를 금지하거나 제한한다(반대로 import가
  자유로우면 이 패턴 자체가 불필요 — 그냥 공유 모듈을 만들면 된다,
  이 경우엔 이 크리스탈 대신 일반적인 코드 재사용 원칙을 따른다).
- 같은 로직을 2곳 이상에서 실제로 반복 사용한다(1곳뿐이면 대조할
  드리프트 위험 자체가 없다).
