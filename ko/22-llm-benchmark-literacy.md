# LLM 벤치마크를 읽는 법 — 무엇을 재고, 뭘 못 재고, 얼마나 믿을 수 있는가

> 🌐 **[Read in English](../en/22-llm-benchmark-literacy.md)**

**콘텐츠 해시**: sha256:3d633bd42059 (본문 기준, 이 두 줄 제외)

[21-spec-first-implementation.md](21-spec-first-implementation.md)가
"GSM8K 56.4%→59.3%" 같은 수치를 근거로 인용했다 — 이 크리스탈은 그
다음 질문에 답한다: **그 수치 자체를 어떻게 읽고, 얼마나 신뢰해야
하는가?** 벤치마크 이름을 인용하는 것과, 그 벤치마크가 뭘 재고 뭘
못 재는지 아는 것은 다르다.

## 1. 주요 벤치마크 지도 — 원문 확인

🟢 아래 전부 논문 원문을 이 크리스탈 작성 과정에서 직접 확인했다.

| 벤치마크 | 무엇을 재는가 | 규모/형식 | 출처 |
|---|---|---|---|
| **GSM8K** | 초등학교 수준 다단계 산술 추론 | 8,500개, 서술형 문제 | Cobbe et al. 2021(OpenAI), [arXiv:2110.14168](https://arxiv.org/abs/2110.14168) |
| **MMLU** | 57개 과목(수학·역사·법·의학 등) 객관식 지식+문제해결 | 57개 과목 종합 | Hendrycks et al. 2020, [arXiv:2009.03300](https://arxiv.org/abs/2009.03300) |
| **HumanEval** | 함수 하나 규모 코드 생성(pass@k로 채점) | 함수시그니처+독스트링+테스트케이스 쌍 | Chen et al. 2021(OpenAI Codex 논문), [arXiv:2107.03374](https://arxiv.org/abs/2107.03374) |
| **SWE-bench** | 실제 GitHub 이슈를 코드베이스 수정으로 해결 | 2,294개, 실제 오픈소스 저장소 12개 기반 | Jimenez et al. 2023, [arXiv:2310.06770](https://arxiv.org/abs/2310.06770) |
| **MT-Bench / Chatbot Arena** | 멀티턴 대화 품질(사람 선호 기준) | 크라우드소싱 쌍대비교 투표(3K 전문가 투표+30K 대화) | Zheng et al. 2023, [arXiv:2306.05685](https://arxiv.org/abs/2306.05685) |

## 2. 벤치마크의 두 근본 유형 — 신뢰도가 다른 이유

### (A) 정적 정답 벤치마크 (GSM8K·MMLU·HumanEval·SWE-bench)
고정된 문제 집합 + 고정된 정답/테스트케이스. **장점**: 재현 가능,
채점 비용이 낮음. **치명적 약점**: **오염(contamination)** — 벤치마크
문제가 모델의 사전학습 데이터에 이미 포함돼 있으면, "추론 능력"이
아니라 "암기"를 재는 것이 된다.

🟢 실측 근거(Yang et al., arXiv:2311.04850 원문 확인): 공개 사전학습
데이터셋(RedPajama-Data-1T, StarCoder-Data)에서 **HumanEval 문제의
8~18%가 이미 겹쳐 있었다.** 더 심각한 건, 단순 문자열 대조(n-gram
overlap) 탐지법은 **패러프레이징이나 번역만 해도 쉽게 우회된다**는
것 — 13B급 모델이 벤치마크를 살짝 바꿔 쓴 데이터로 과적합해 GPT-4급
성능을 흉내낸 사례까지 실측됐다.

### (B) 동적 사람 평가 (Chatbot Arena)
고정된 문제 집합이 없다 — 실시간으로 사람이 두 모델의 답을 비교
투표한다. **장점**: 오염이 구조적으로 불가능(문제 자체가 계속 새로
생김). **약점**: 비용이 높고, 표본(누가 투표하는가)의 대표성 문제가
있다.

🟢 실측 근거(Zheng et al. 2023 원문 확인): GPT-4를 판정자로 쓰면 **사람과
80% 이상 일치**하는데, 이건 "사람들끼리 서로 일치하는 비율"과 같은
수준이다 — 즉 LLM 판정자가 완벽하지 않은 건 사람 판정자도 원래 완벽하지
않기 때문이라는 것도 같이 확인된 사실이다.

**결론**: (A)류 벤치마크 수치를 인용받으면 "이 모델이 이 정확한 문제를
학습 중에 봤을 가능성"을 항상 의심 항목에 넣는다. (B)류는 오염 위험은
낮지만 "이 투표 표본이 실제 사용자층을 대표하는가"를 따로 의심한다.

## 3. 벤치마크가 절대 못 커버하는 것

- **정답이 없는 작업**: 창작, 전략적 판단, 가치 판단, 관계의 정서적
  뉘앙스 — 위 벤치마크 전부 "정답이 하나로 정해진" 태스크 전제다.
  [01-definition-of-done.md](01-definition-of-done.md) 8번 기준이
  이미 "사람이 더 나은 영역엔 AI 비교우위 근거를 억지로 안 채운다"고
  다루는 것과 같은 경계.
- **태스크 규모/맥락**: HumanEval은 **함수 하나** 규모다. 실제
  멀티파일 소프트웨어 프로젝트(예: 이 프레임워크의
  [09-project-structure-template.md](09-project-structure-template.md)가
  다루는 스케일)와는 난이도·실패 모드 자체가 다르다 — SWE-bench가
  이 간극을 메우려 만들어졌지만, 그마저도 원문이 스스로 밝히듯
  **최고 성능 모델도 해결률이 매우 낮았다**(공개 당시 Claude 2가
  1.96% 해결) — 실제 소프트웨어 엔지니어링은 함수 단위 벤치마크보다
  훨씬 어렵다는 뜻이다.
- **벤치마크 포화(saturation)의 해석 함정**: MultiArith(83.8%→91.8%)처럼
  이미 baseline이 높으면, 남은 오류가 "더 쉬운데 운이 없어서 틀린 것"이
  아니라 "정말 어려운 잔차만 남은 것"일 수 있다 — 포화된 벤치마크에서의
  같은 %p 개선은 초반 %p 개선보다 실제로는 더 어려운 성취일 수 있다는
  뜻이라, 숫자만 보고 두 구간을 같은 무게로 비교하면 안 된다.

## 4. 절대 개선 vs 상대 개선 — 가장 흔한 오독

크리스탈 21이 인용한 "Pass@1 최대 +25.4%"는 **상대 개선(relative
improvement)**이지 절대 퍼센트포인트(percentage point)가 아니다 —
즉 기준선이 40%였다면 40%×1.254 ≈ 50.2%(절대 +10.2%p)라는 뜻이지,
"40%에서 65%로 뛰었다"는 뜻이 아니다(21번 크리스탈 본문은 실제로
"상대 개선"이라고 정확히 표기했다 — 정정할 오류가 아니라, 표기가
정확했음에도 **두 종류(절대/상대)가 한 문서 안에 섞여 있으면 독자가
훑어 읽다 놓치기 쉽다**는 위험을 보여주는 사례로 남긴다). 반면 GSM8K의
"56.4%→59.3%"는 **절대 %p 차이**(59.3-56.4=2.9%p, 상대로 환산하면 약
+5.1%)다. **인용할 때마다 "이게 절대냐 상대냐"를 문장 안에 명시하는
습관이 필요하다**
([03-epistemic-immunity-catalog.md](03-epistemic-immunity-catalog.md)
2번 "가짜 정밀함"과 같은 계열의 함정 — 숫자가 정밀해 보여도 무엇을
재는 숫자인지 불명확하면 정밀함이 오히려 오해를 키운다).

## 5. 새 벤치마크 수치를 인용받았을 때 체크리스트

- [ ] **정적 벤치마크인가, 동적 사람평가인가** — 정적이면 오염 가능성을
      의심 목록에 넣는다.
- [ ] **절대 %p인가, 상대 %인가** — 둘을 구분해서 다시 쓴다.
- [ ] **표본 크기·신뢰구간·반복 실행 여부**가 논문에 있는가 — 없으면
      "이 차이가 노이즈보다 큰지"를 판단할 근거가 없다는 뜻이니 그렇게
      명시한다.
- [ ] **이 벤치마크의 태스크 규모/분포가 지금 판단하려는 실사용 맥락과
      얼마나 가까운가** — 함수 하나 규모 벤치마크 수치를, 멀티파일
      프로젝트 빌드의 근거로 그대로 끌어오지 않는다
      ([21-spec-first-implementation.md](21-spec-first-implementation.md)의
      "범위 경계" 절과 동일 원칙).
- [ ] **벤치마크 순위 개선이 실사용 체감으로 이어진다는 근거가 별도로
      있는가**, 아니면 벤치마크 개선 자체를 최종 목표로 착각하고
      있는가([05-autonomous-agent-operating-principles.md](05-autonomous-agent-operating-principles.md)의
      "최종 수혜자는 사용자다" 원칙과 연결 — 벤치마크 1위가 목적이
      아니라 사용자 결과가 목적이다).
