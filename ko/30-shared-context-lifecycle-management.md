그보다 한 단계 위 — **여러 세션에 걸쳐 누적되는 공유 컨텍스트 파일 자체가
계속 자라날 때 어떻게 관리하는가**, 그리고 **압축이 정보를 잃어도 다음
세션이 동등한 수준으로 복구하려면 무엇이 필요한가**를 다룬다. [06-self-
improving-heuristics-loop.md](06-self-improving-heuristics-loop.md)의
"메모리 상한" 원칙이 규칙 목록 하나에 적용하는 걸, 이 크리스탈은 프로젝트
전체의 공유 컨텍스트 파일군에 일반화한다.

## 근거

- 🟢 **MemGPT**(Packer et al., 2023, [arXiv:2310.08560](https://arxiv.org/abs/2310.08560)) —
  원문 확인. 핵심 은유: "메인 컨텍스트(책상)가 꽉 차면 오래된 항목을
  외부 스토리지(창고)로 내보내고, 필요할 때 검색해서 다시 불러온다." 이
  크리스탈의 "날짜 경계 아카이빙 + 검색 폴백" 축이 직접 대응한다.
- 🟢 **Anthropic, "Effective context engineering for AI agents"**(2025-09-29,
  공식 엔지니어링 블로그) — 이미 [16번](16-context-engineering-principles.md)의
  근거이기도 하지만, 이 크리스탈은 그중 16번이 아직 안 담은 두 원칙을
  가져온다: (1) **"recall 먼저, precision은 나중"** — 압축은 관련 있을
  수도 있는 걸 먼저 넓게 회수하고, 정확한 좁히기는 그다음 단계에 맡기는
  순서가 안전하다. (2) **도구 호출 결과(tool result)를 지우는 게 압축
  중 가장 위험이 낮은 축소 대상**이다 — 오래된 원시 조회 결과를 다시
  읽어서 득 보는 경우는 드물기 때문.
- 🟢 공식 Claude Code Best Practices — "비대해진 규칙 문서는 AI가 실제
  지시를 무시하게 만든다"는 취지의 경고(이미 [26-grounding-validity-
  audit.md](26-grounding-validity-audit.md)에서 검증된 인용을 재사용).

## 핵심 메커니즘

### 1. 비율 기반 이중 임계값
절대 줄 수·바이트 수가 아니라 **기준선 대비 비율**로 경고/긴급 두 단계를
둔다(예: 기준선의 1.0배에서 경고, 1.5배에서 긴급) — 파일마다 "적정 크기"가
다르므로 절대값 하나를 전체에 강제하면 어떤 파일엔 너무 이르고 어떤
파일엔 너무 늦다. MemGPT 자신의 70%/100% 경고·퇴거 이중 임계값과 같은
발상이다.

### 2. 무손실 압축 우선 원칙
압축은 "요약해서 압축"이 아니라 **사실·수치·날짜·결정을 전부 보존하고
연결 서사(접속사, 설명 문장)만 걷어내는 것**이 기본이다. 정보 손실은
아래 3~5번 메커니즘(날짜 경계 분리·파일 분할)으로 옮기는 것이지, 압축
단계 자체에서 발생시키지 않는다 — "요약하면 짧아지지만 재구성 불가능한
디테일이 빠진다"는 위험을 원천 차단하는 순서다.

### 3. 문서 유형별 압축 여지 판단
같은 "압축 대상"이라도 **로그형 문서**(append-only, 과거 기록이 다시
바뀔 일 없음)와 **활성 규칙서형 문서**(현재 유효한 규칙 자체가 본문)는
압축 여지가 다르다 — 로그형은 오래된 절반을 통째로 날짜 경계로 잘라
아카이브해도 안전하지만, 규칙서형은 그렇게 자르면 "지금 유효한 규칙"이
잘려나갈 위험이 있어 문장 단위 압축(중복 제거, 표현 축약)만 적용한다.

### 4. 날짜 경계 아카이빙
로그형 문서가 임계값을 넘으면, 요약하지 않고 **오래된 절반(또는 일정
날짜 이전)을 그대로 별도 아카이브 파일로 옮긴다** — 정보 손실이 0이다.
현재 파일은 최근 항목만 유지해 가벼워지고, 과거 항목이 필요하면 아카이브
경로를 알고 있으므로 언제든 다시 읽을 수 있다.

### 5. 읽기 빈도 기반 파일 분할
한 파일 안에 있던 여러 절 중 **특정 절을 실제로 참조하는 소비자가
소수(또는 하나)뿐**이라면, 그 절을 별도 파일로 떼어낸다 — 모든 세션이
매번 읽는 "핵심" 파일은 작게 유지되고, 특정 맥락에서만 필요한 세부는
그 맥락이 실제로 필요할 때만 열람된다. 이건 압축이 아니라 **접근 경로
재설계**다 — 정보는 그대로 남고 "기본으로 로드되는가"만 바뀐다.

### 6. 검색을 압축의 안전판으로
압축·분할로 어떤 정보가 기본 로드 경로에서 빠지더라도, **기록 자체를
지우지 않고 검색 가능한 상태로 남기면** 나중에 실제로 필요해졌을 때
비용 없이(LLM 호출 없이) 되찾을 수 있다 — 예: 타임스탬프가 붙은 append-
only 로그를 파싱해 최신성×관련성(문자열 일치 횟수) 두 신호로 점수를
매겨 상위 K개만 반환하는 결정론적 스크립트. 임베딩이나 LLM 호출 없이
grep 수준의 계산만으로 작동한다는 게 핵심 — 압축의 "안전판"이 그 자체로
비용을 거의 안 쓴다.

### 7. 세션 시작 시 고정 순서 부트스트랩
세션 압축(대화 요약)은 세션이 끊기지 않는 한에서만 작동한다 — **완전히
새 세션이 "이어서 진행해"로 시작하면 압축 요약 자체가 존재하지 않는다.**
이 간극을 메우려면 압축에 의존하지 않고, **세션 시작 시 항상 같은 순서로
읽는 소수의 상태 파일**을 고정해둔다(예: 현재 진행 상황 → 선호/맥락 →
품질/검증 상태 → 콘텐츠 색인). 순서가 중요한 이유: 앞 파일의 정보가
뒤 파일을 해석하는 맥락이 되기 때문 — 순서를 바꾸면 같은 파일들을
읽어도 재구성되는 그림이 달라질 수 있다.

## 압축 중 보존되는 것 vs 위험한 것

| 유형 | 압축(요약)에서 살아남는가 |
|---|---|
| 명시적 결정·수치·날짜 | 대체로 보존됨(요약 모델이 구조화된 사실을 우선 보존하는 경향) |
| 사용자의 원문 그대로의 요청 | 대체로 보존됨 |
| 과정상의 뉘앙스(왜 그 방법을 버렸는지 등 세부 이유) | 위험 — 압축될수록 소실 가능성 큼, 파일에 명시적으로 적어둬야 살아남음 |
| 도구 호출의 원시 출력(과거 조회 결과 전문) | 압축의 안전한 축소 대상(위 근거의 2번) — 잃어도 재조회 비용이 낮음 |

## 정직한 한계

- 구체적 임계값(경고 1.0배/긴급 1.5배 등)과 파일 분할 사례는 특정
  프로젝트 하나의 운영 데이터에서 나온 것이라 그대로 이식 가능한 수치가
  아니다 — 각 프로젝트가 자신의 재작성 빈도·파일 성격에 맞게 기준선을
  다시 잡아야 한다.
- 압축이 실제로 무엇을 보존/소실하는지의 표는 한 압축 엔진(Claude Code
  자체)을 직접 관찰한 결과이지, 모든 LLM 압축 구현에 그대로 일반화된다는
  외부 검증은 없다.
