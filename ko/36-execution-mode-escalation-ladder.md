# 실행 모드 에스컬레이션 사다리 — 언제 병렬화·분리 실행으로 올라갈지

> 🌐 **[Read in English](../en/36-execution-mode-escalation-ladder.md)**

**버전**: 1.0.2
**콘텐츠 해시**: sha256:2991a90703cf (본문 기준, 이 두 줄 제외)

**검증 강도**: 🟡 원본 프로젝트 안에서 반복 사용되는 스킬 하나의 설계로
실전 검증(자체 eval 케이스 통과 기록 있음)됐지만, 이 정확한 4단계 사다리
구조를 다른 프로젝트나 다른 팀에서도 쓰는지까지는 확인하지 못했다 —
외부 표준 대조는 없음, 이 프로젝트 내부의 반복 검증된 관행.

AI 에이전트가 작업을 받았을 때 "지금 방식(단일 세션·순차)으로 계속할지,
병렬화·분리 실행으로 올릴지"를 매번 감으로 정하면 두 방향으로 틀린다 —
항상 순차로만 하면 명백히 독립적인 하위작업도 느리게 처리하고, 항상
병렬화부터 시도하면 설정 비용만 늘고 맥락이 흩어져 오히려 부정확해진다.
이 크리스탈은 **"기본값은 항상 가장 싼 옵션, 구체적 신호가 있을 때만
한 단계씩 올라간다"**는 명시적 사다리를 정의한다.

## 4단계 레벨

| 레벨 | 무엇을 하는가 | 언제 |
|---|---|---|
| L0. 단일 세션 순차 | 지금 방식 그대로 | **기본값** — 아래 신호가 하나도 없으면 이게 정답 |
| L1. 세션 내 서브에이전트 | 독립적인 탐색/리서치/리뷰를 위임하고 결과만 받음 | 하위작업이 가볍고 1회성일 때 |
| L2. 다단계 파이프라인 도구 | 다단계 파이프라인 + 병렬 팬아웃 + 검증을 코드로 조율 | 하위작업이 여러 단계고 각 단계 검증이 필요할 때 |
| L3. 완전히 분리된 병렬 실행 환경 | 독립된 브랜치·독립된 작업공간에서 별도 세션을 물리적으로 병렬 실행 | 서로 무관한 프로젝트/기능을 동시에 진행할 때 |

레벨이 높아질수록 강력하지만 설정 비용도 커진다 — **L0에서 시작해서,
아래 신호가 나타날 때만 한 단계씩 올라간다.**

## 에스컬레이션을 정당화하는 4가지 신호 — 하나라도 없으면 안 올라간다

1. 지금 하려는 일이 **서로 독립적인 하위작업 3개 이상**으로 쪼개지는가.
2. **오래 걸리는 작업**을 시작해놓고 결과가 나올 때까지 그냥 기다리고
   있는가 — 백그라운드로 돌려놓고도 다른 걸 안 하고 화면만 보는 경우.
3. 결과가 틀리면 **비용이 크고**, 그런데도 **판단이 한 관점에만** 의존
   하고 있는가.
4. **서로 무관한 두 작업/맥락**을 같은 세션에서 번갈아 하느라, 매번
   맥락을 다시 설명하고 있는가.

**하지 말아야 할 것**: 맥락이 계속 이어져야 하는 논의(설계를 조금씩
다듬는 대화), 좁고 깊은 하나의 작업을 단계별로 다듬는 것, 작은 수정을
빠르게 여러 번 주고받는 것 — 이런 경우 억지로 여러 세션/에이전트로
쪼개면 맥락이 흩어져 **더 느려지고 더 부정확해진다.** "병렬화 = 항상
좋음"이 아니라 "특정 신호가 있을 때만 병렬화"가 맞는 프레임이다.

## 정확성 레버 (L0에서도 바로 쓸 수 있는 가장 싼 것)

혼자 판단하면 스스로의 사각지대를 못 본다 — 중요한 산출물이면 "이 결과를
한 번 반박해봐"라고 스스로(또는 별도 실행 단위)에게 시키는 게 에스컬레이션
없이 L0 안에서 바로 쓸 수 있는 가장 저렴한 정확성 레버다.

## 창의성 레버 — 여러 독립 시도 후 종합("judge panel")

순차 대화는 첫 아이디어에 고착(anchoring)되기 쉽다. **정답이 없는
설계/기획/브레인스토밍 질문일수록**, 서로 다른 관점(예: 완성도 우선/
위험 우선/사용자 우선)으로 독립적인 초안을 각각 만들고 비교·종합하면
실제로 더 창의적인 결과가 나온다. 반대로 정답이 명확한 문제엔 오버킬이라
쓰지 않는다.

**이게 [04-eval-engineering-methodology.md](04-eval-engineering-methodology.md)의
self-consistency와 다른 지점(G3)**: self-consistency는 **정답이 검증
가능한 판정**의 노이즈를 다수결로 줄이는 것이고, 이 레버는 **정답이
없는 개방형 산출물**의 첫 아이디어 고착을 피하려고 서로 다른 관점을
의도적으로 만드는 것이다 — 목적(분산 축소 vs 관점 다양화)이 반대에
가깝다.

## 판단 흐름

```
새 작업을 받음
  ├─ 지금 세션 맥락과 무관한 별개 작업인가? → L3
  ├─ 독립적인 하위작업 3개 이상 + 단계별 검증이 필요한가? → L2
  ├─ 독립적인 하위작업이 있지만 가볍고 1회성인가? → L1
  ├─ 정답이 없는 설계/기획/브레인스토밍인가? → judge panel(여러 독립 시도 → 종합)
  └─ 위 어디에도 안 걸림 → L0 그대로(병렬화가 항상 좋은 게 아님을 기억)

+ 오래 걸리는 작업을 이미 시작했다면: 기다리지 말고 그 사이 다른 요청을 이어서 처리한다.
+ 결과가 나온 뒤 정확성이 중요한 산출물이면: 별도 관점으로 한 번 더 검증할지 고려한다.
```

## 이것이 09번과 다른 지점 (G3)

[09-project-structure-template.md](09-project-structure-template.md) 3.3절의
"Skill vs Workflow" 결정 기준은 **하나의 실행 로직을 어느 포맷으로 작성할지**(단일
호출 vs 다단계 파이프라인)를 정하는 좁은 판단이고, 이 크리스탈의 L2가
정확히 그 지점에 대응한다. 이 사다리는 그보다 넓은 범위 — **작업을
받는 시점에, 애초에 병렬·분리 실행으로 갈지 말지 자체**를 신호 기반으로
판단하고, 09번이 다루지 않는 L3(완전히 분리된 병렬 실행 환경)까지
포함한다.

## 정직한 한계

- 4단계 사다리 구조 자체는 원본 프로젝트 안에서 반복 사용되는 스킬
  하나로 실전 검증됐다(자체 eval 케이스 통과 기록 있음) — 다만 단일
  스킬의 설계라 이 정확한 임계값·레벨 구분이 다른 프로젝트에도 그대로
  최적인지는 검증되지 않았다. 신호 자체(독립 하위작업 개수, 대기 비용,
  판단 관점 수, 맥락 전환 빈도)는 일반화 가능하지만, "정확히 3개
  이상"류 구체적 문턱값은 각 프로젝트가 자기 상황에 맞게 재조정할
  여지가 있다.
