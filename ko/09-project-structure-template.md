# AI-에이전트-관리형 프로젝트 구조 템플릿 — 5레이어 아키텍처

> 🌐 **[Read in English](../en/09-project-structure-template.md)**

**버전**: 1.0.3
**콘텐츠 해시**: sha256:27aa768c6d2d (본문 기준, 이 두 줄 제외)

**검증 강도**: 🟢 C4 모델(arc42)의 줌 레벨 개념을 원용했고, 5레이어
구조·13단계 순서는 원본 프로젝트가 실제로 이 순서대로(또는 비슷한
순서로) 자라난 이력을 사후 정리한 것.

**전체 조망(무엇이 있는가)**과 **실제로 어떻게 만드는가(스키마·순서)**를
둘 다 담는다 — 오버뷰만 있으면 재구축이 불가능하다는 게 이 템플릿의
출발점이다 — [C4 모델](https://arc42.org/overview/)의 "줌 레벨"(Context
→ Container → Component)을 빌린 구조다.

## 1. 아키텍처 — 5개 레이어

```
tasks/          "뭘 하는 작업인가" 정의(메타데이터: 감독등급, 확신도등급,
                도메인, 실행주기 등)
  ↓ 1:1 대응
실행 로직 레이어  반복이면 단일 실행 스킬, 다단계 파이프라인이면 워크플로
  ↓ 누적
공유 컨텍스트 레이어  작업을 가로질러 쌓이는 맥락(선호·이력) — 반복될수록
                품질이 좋아지는 이유
  ↓ 거버넌스
거버넌스 레이어  "어떻게 판단하고 뭘 기준으로 완성됐다고 보는가" — DoD/DoR/
                의사결정 로그/지시 레지스트리/용어집
  ↓ 완성품
제품 레이어      사용자에게 보여줄 완성된 산출물
```

각 레이어는 독립적으로 확장 가능하다 — 새 작업을 추가해도 거버넌스 문서를
매번 새로 쓸 필요 없고(기존 DoD/DoR 기준을 그대로 적용), 새 제품을 추가해도
작업 레이어 구조를 안 건드린다.

## 2. 핵심 개념 대응표

| 축 | 값 | 뜻 |
|---|---|---|
| 실행가능성 분류 | 끝이 있음/지속됨/참고자료/보류 | 이 항목이 뭔지(PARA류 분류) |
| 도메인 | work/life/meta/cross | 작업이 직업/개인생활/인프라/의도적 통합 중 무엇인가 |
| 감독등급(oversight_gate) | none/notify/confirm | 실행이 비가역적 행동을 포함하는가(**행동** 축) |
| 확신도등급(confidence_gate) | none/flag/ask | 산출물 내용의 확신도(**내용** 축 — 행동 축과 다름) |
| 완성 기준의 방향 | DoD → DoR | "다 만들었다"의 기준 → "시작해도 된다"의 기준(사후 → 사전) |

## 3. 레이어별 상세 스펙 — 그대로 복사해서 채우면 재구축 가능한 수준

### 3.1 작업 정의 — 정확한 스키마

메타데이터(YAML frontmatter) 전체 필드:
```yaml
---
name: <task-name>
status: draft | active | paused | done | note
cadence: one-off | daily | weekly | per-sprint | on-demand | as-needed | monthly
success_criteria: "무엇이 나오면 성공인지 한 문장"
tools: [WebSearch, WebFetch, Bash, ...]        # 실제 쓰는 도구만
executor: Skill | Workflow | 즉석 세션(ad-hoc)
oversight_gate: none | notify | confirm         # 행동의 비가역성 축
confidence_gate: none | flag | ask               # 산출물 확신도 축 (oversight_gate와 다른 축)
domain: work | life | meta | cross               # 어느 생활/업무 영역인가
irreversible_actions: []   # 예: [overwrite_existing_file, git_commit, git_push, external_send]
---
```
본문 필수 섹션(순서 고정): `## 목적` → `## 입력` → `## 출력` → (반복형이면
`## 누적되는 맥락` 추가) → `## 왜 이 작업이 AI 관리에 적합한가`(아래 6항목
체크리스트) → `## 실행` → `## AI 비교우위`(일반론 금지, 사람이 실제로
겪는 병목을 한 줄 이상 구체적으로).

**선택 섹션 — 범위 밖(중복 방지)**: 작업이 늘어날수록 인접 작업과
경계가 흐려진다("이거 저 작업이랑 뭐가 다르지?"). 겹칠 만한 작업이
있으면 `## 범위 밖`에 그 작업 이름과 함께 "이 작업은 X를 다루지 않는다,
X는 <다른 작업 이름>을 쓴다"고 명시한다 — 나중에 같은 질문이 반복될
때마다 새로 판단하지 않고 이 한 줄이 답한다.

**적합성 체크리스트 6항목** — 새 아이디어를 작업으로 편입할지 심사하는 기준:
- [ ] 출력 형식이 구조화되어 있는가
- [ ] 같은 템플릿으로 반복 가능한가
- [ ] 조사→초안→검증 단계로 분해되는가
- [ ] 틀려도 비용이 낮고 검토가 쉬운가
- [ ] 최신 정보가 필요하면 검색 도구로 보완 가능한가
- [ ] 반복될수록 축적된 선호/맥락이 품질을 높이는가

**부트스트랩 절차**: 템플릿을 새 작업 디렉터리로 복사 → 위 메타데이터·
섹션 채움 → 실행 방식에 맞게 실행 로직 작성 → 평가 케이스 추가(3.4절) →
민감정보 스캔 실행 → 루트 인덱스에 도메인 값과 함께 한 행 추가.

### 3.2 단일 실행 스킬 — 실행 로직(반복 단일 실행용)

```markdown
---
name: <task-name>
description: 한 줄 설명(트리거 조건 포함)
---

## 절차
1. **입력 확인**: 필요한 정보를 확인하고, 빠지면 되묻는다.
   공유 컨텍스트의 관련 기록이 있으면 참고한다.
2. **조사**: 최신성이 필요하면 검색 도구를 쓰고, 출처를 남긴다.
3. (도메인별 단계들)
4. **산출물 작성**
5. **저장**: 정해진 경로에 저장할지 물어본다.
6. **맥락 업데이트**: 새로 드러난 선호를 공유 컨텍스트에 추가 제안.

## 원칙
- 확실하지 않은 정보는 "확인 필요"로 표시(추측 금지)
- 제3자 정보는 실명 대신 일반화, 민감정보는 산출물에 저장 안 함
```

**P99 희소·고위험 시나리오 등록부(해당 도메인만)**: 사람의 안전·건강·재정
등 되돌리기 어려운 결과와 맞닿는 도메인을 다루는 스킬은, 위 본문과
별도로 `<task-dir>/p99-scenarios.md` 하나를 둔다 — 발생 확률은 낮지만
결과가 심각한 입력(의료 응급 신호, 학대·자해 신호, 사기 징후 등)을
목록화하고, **이 시나리오가 감지되면 스킬의 평소 절차보다 우선한다**는
규칙을 명시한다. 별도 파일로 두는 이유: 매일 실행되는 평소 절차의
컨텍스트를 무겁게 하지 않으면서도, 드물게 필요할 때는 놓치지 않게
한다 — 이름은 SRE의 p99 지연시간(꼬리 확률·고심각도) 관측 관행에서
빌려온 은유이지 그 문헌이 이 안전-트리아지 메커니즘 자체를 검증한다는
뜻은 아니다.

### 3.3 다단계 워크플로 — 실행 로직(파이프라인용)

**Skill과의 결정 기준**: 반복이지만 단일 호출로 끝나면 Skill, 조사→초안→
독립검증→비교→최종화처럼 여러 단계가 있고 병렬화 여지가 있으면 Workflow.

```js
export const meta = {                 // 반드시 순수 리터럴(변수·계산 불가)
  name: "task-name",
  description: "...",
  phases: [{ title: "Discover", detail: "..." }, { title: "Digest", detail: "..." }],
};

phase("Discover");
const found = await agent(`...`, { schema: SOME_SCHEMA });

const results = await pipeline(              // 각 아이템이 독립적으로 단계를 통과
  items,
  (item) => agent(`1단계 프롬프트`, { phase: "Digest", label: `step1:${item.id}` }),
  (prev, item) => parallel([                  // 병렬화 지점(예: 정량/정성 독립 검증)
    () => agent(`검증 A`, { phase: "Digest" }),
    () => agent(`검증 B`, { phase: "Digest" }),
  ]).then(([a, b]) => ({ ...prev, a, b })),
);
return { results };
```

**함정(재구축 시 반드시 알아야 함)**: 워크플로 실행 도구가 "이름으로 등록된
스크립트"와 "경로로 직접 지정한 스크립트"를 다르게 취급하는 구현이면(세션
중 등록 시점 스냅샷을 재사용해 파일을 고쳐도 반영이 안 되는 경우), 편집
직후엔 반드시 경로 직접 지정 방식으로 호출해 결과물로 반영을 확인한 뒤에만
이름 호출로 넘어간다.

### 3.4 평가 케이스 — 검증

```yaml
---
target_type: skill | workflow
rubric:
  - "판정 기준 문장 1 — 이 작업의 산출물이 반드시 갖춰야 하는 성질"
  - "판정 기준 문장 2 ..."
pass_threshold: 0.8
---

## 케이스 1: <시나리오 이름>
### 입력
(구체적 입력값)
### 기대 동작
- (이 입력에서 반드시 나와야 하는 것)
```
rubric은 일반론이 아니라 "이 도메인에만 해당하는 구체적 기준"이어야 한다.

### 3.5 공유 컨텍스트 레이어

| 파일 | 역할 |
|---|---|
| 선호/이력 파일 | 작업을 가로질러 쌓이는 선호(취향, 반복되는 패턴 등) |
| 알림 수신처 | 재식별 지문 최소화를 위해 반복 기재 안 함 |
| 페르소나 정의 | (있는 경우) |
| 재사용 프롬프트 조각 | |
| 비용 사용 로그 | 실측 로그(오래되면 아카이브) |
| 로컬 전용 디렉터리 | 민감정보를 버전관리 추적 범위 밖에 두는 곳 |

### 3.6 거버넌스 레이어 — 실제로 필요한 최소 세트

전부 한 번에 필요한 게 아니다 — **부채가 쌓일 때 그 부채 종류에 맞는
문서를 신설**하는 게 맞는 순서다:

| 최소 세트 | 언제 필요해지는가 |
|---|---|
| Definition of Done | 작업이 3~5개를 넘어 "다 만들었다"는 기준이 사람마다 달라지기 시작할 때 |
| 프롬프트/개인정보 가드레일 + 스캐너 | 개인정보를 다루는 첫 작업이 생기는 순간(미루면 안 됨) |
| 평가(eval) 인프라 | 산출물 품질을 매번 눈으로만 확인하기 버거워질 때 |
| 부채 분류 체계 | "검증 안 된 채 쌓인 게 얼마나 되는가"를 재야 할 때 |
| 의사결정 로그 + 지시 레지스트리 | 자율 판단·지시가 누적돼 "이거 왜 이렇게 정했더라"가 반복될 때 |
| 아키텍처 결정 기록(ADR) | 구조적 설계 결정(왜 이 방식을 택했나)이 재검토 가치가 생길 때 |
| 사후기록(postmortem) 폴더군 | 첫 사고가 실제로 나는 순간(미리 폴더만 만들어두고 비워둬도 됨) |

### 3.7 제품화 파이프라인

```
1. 원 산출물(발굴→요약→검증→정리)
        ↓ 사람이 보기 좋게 재구성(자동 변환 아님, 직접 작성)
2. 제품 HTML(디자인 토큰 CSS, 라이트/다크 대응)
        ↓ 발행
3. 실제 발행 URL
        ↓ 색인
4. 허브 페이지 — 통계 + 카드 목록
        ↓ 기록
5. 배치별 README — 뭘 했고, 갱신된 통계, 남은 백로그
```
제품 HTML의 CSS는 재사용 토큰 시스템으로 만든다 — 새 제품을 만들 땐 기존
파일 하나를 통째로 복사해 내용만 바꾸는 게 디자인 시스템을 매번 새로 짜지
않는 실용적 관행이다.

## 4. 제로부터 재구축하는 단계별 순서

뒤 단계가 앞 단계 없이는 의미가 없다:

1. **프로젝트 뼈대**: 루트 인덱스(빈 작업 목록표만이라도), 일회성/반복형
   작업 템플릿 — 이게 없으면 작업을 매번 처음부터 설계해야 한다.
2. **최소 DoD**(처음엔 3~4개 기준만이어도 됨) — "완성"의 공통 기준 없이
   작업을 늘리면 나중에 전부 재작업해야 한다.
3. **첫 3~5개 작업을 단일 실행 스킬로 직접 만들어본다**(간단한 것부터).
   이 단계에서 3.1~3.2의 스키마가 실전 검증된다.
4. **프롬프트/개인정보 가드레일 + 스캐너** — 개인정보를 다루는 작업이
   하나라도 생기기 전에 반드시 먼저(사후 추가는 이미 노출된 걸 지우는
   훨씬 비싼 작업이 된다).
5. **평가(eval) 인프라** — 이제 작업이 늘어 눈으로 매번 품질을 확인하기
   어려워진 시점. 케이스 기반 루브릭 채점 도입.
6. **사후기록 폴더군을 미리 만들어둔다**(비어 있어도 됨) — 첫 사고가
   실제로 나면 그 즉시 기록할 자리가 있어야 "그때 가서 만들자"로
   미뤄지지 않는다.
7. **작업을 도메인 다양하게 늘린다**(예: 업무 + 개인생활 양쪽) — 이
   시점에 이미 도메인 축을 처음부터 넣어두면 나중에 전부 소급 태깅할
   필요가 없다(교훈: 나중에 필요해질 축은 처음부터 스키마에 넣는 게 싸다).
8. **의사결정 로그 + 지시 레지스트리** — 판단 근거를 "그때그때 커밋
   메시지에만" 남기지 말고 한곳에 모으기 시작하는 시점. 판단이 5~10건
   쌓이면 이게 없으면 이미 헷갈리기 시작한다.
9. **ADR** — 구조적 결정(왜 이 아키텍처, 왜 이 필드)이 재검토할 가치가
   생기는 시점(대개 8번과 비슷한 시기).
10. **반복형(cadence≠one-off) 작업으로 확장** — 이 시점부터 감독등급
    (무인 실행 중 confirm 금지 규칙)이 실질적으로 중요해진다.
11. **첫 제품 파이프라인 구축**(3.7 참고) — 콘텐츠 축적형 작업을 하나
    골라 검증 로직을 강화하고, 사람이 보는 최종 결과물을 별도 레이어로
    분리한다. **이 순서가 중요하다** — 검증 로직이 부실한 채로 먼저
    제품화하면 산출물 개수만 늘고 신뢰도는 안 늘어난다.
12. **cross-cutting 축을 필요해질 때 추가**(확신도등급, 도메인 등) —
    소급 적용은 스크립트로 일괄 처리한다 — 수십 개를 손으로 하나씩
    고치지 않는다.
13. **2차 거버넌스**(거버넌스의 거버넌스): 문서 개수가 늘어나면 우선순위
    지도, 용어 통일 사전, 재조회 방지 자동 인덱스, 이 설계도 자체가
    필요해진다 — 너무 일찍 만들면 과한 인프라, 너무 늦으면 이미 인지부채가
    쌓인 뒤다.

## 5. 이 템플릿을 어떻게 검증할 것인가

이 5레이어 구조는 실제 프로젝트가 커지면서 이 순서대로(또는 비슷한
순서로) 자연스럽게 형성된 걸 사후에 정리한 것이다 — 처음부터 이 13단계를
계획하고 만든 게 아니라, "빅뱅"처럼 한꺼번에 만들어진 뒤 이후 계속 다듬어진
이력이 실제로 있다. 새 프로젝트에 이식할 때는 13단계를 순서대로 따라가되,
각 단계에서 "이게 지금 정말 필요한가"를 판단하며 너무 이른 인프라 투자를
피하는 걸 권한다(6절의 "너무 일찍 만들면 과한 인프라" 경고와 같은 원칙).
