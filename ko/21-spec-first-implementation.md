# 명세 우선 구현 — 계획을 먼저 쓰고 그 계획대로 만드는 것의 실제 효과

> 🌐 **[Read in English](../en/21-spec-first-implementation.md)**

**버전**: 1.0.2
**콘텐츠 해시**: sha256:3ed20fa20b84 (본문 기준, 이 두 줄 제외)

"기획서/설계 명세를 AI에게 먼저 그리게 한 다음 그걸로 이행시키는" 접근을
그냥 "좋은 습관"으로 권하지 않는다 — 이 크리스탈은 **그게 실제로 효과가
있다는 정량적 근거**와, **그 근거가 어디까지만 적용되는지**를 같이
남긴다.

## 이름 — 세 계보가 겹쳐 있다

단일 기법이 아니라 서로 다른 시기·분야에서 수렴한 패턴이다:

1. **Plan-and-Solve Prompting**(Wang et al. 2023, [arXiv:2305.04091](https://arxiv.org/abs/2305.04091)) — LLM
   추론 연구. "먼저 계획을 세우고, 그 계획대로 실행한다"를 프롬프트
   기법으로 정식화.
2. **Self-Planning Code Generation**(Jiang et al. 2023, [arXiv:2303.06689](https://arxiv.org/abs/2303.06689),
   ACM TOSEM 게재) — 코드 생성 연구. 요구사항에서 먼저 계획을 뽑고, 그
   계획을 따라 코드를 순차 생성.
3. **명세 우선/테스트 주도 개발(TDD)** — LLM 이전부터 있던 소프트웨어
   공학 관행(Kent Beck, 2002). "구현 전에 테스트/명세부터 쓴다."
4. 참고: 이건 연구 개념에 그치지 않고 실제 코딩 에이전트 도구의
   **제품 기능**(예: "계획 모드")으로도 이미 채택돼 있다 — 실전 채택
   사례로 읽을 수 있다.

## 근거 (1차 자료 확인) — 실제 수치

🟢 두 논문 원문을 이 세션에서 직접 확인했다(추정 아님).

**Plan-and-Solve(PS+) vs Zero-shot-CoT**(같은 모델, 프롬프트 방식만 다름):

| 벤치마크 | Zero-shot-CoT | PS+ | 8-shot Manual-CoT(참고) |
|---|---|---|---|
| GSM8K | 56.4% | **59.3%** | 58.4% |
| SVAMP | 69.9% | **75.7%** | 80.3% |
| MultiArith | 83.8% | **91.8%** | 93.6% |

먼저 계획을 세운다는 것만으로, 예시(few-shot) 없이도 few-shot 수준에
근접하거나 뛰어넘는다.

**Self-Planning Code Generation**: 직접 코드 생성 대비 Pass@1 **최대
+25.4%** 상대 개선, CoT 방식 코드 생성 대비도 **최대 +11.9%** — 사람
평가에서도 정확성·가독성·견고성 세 축 모두 개선 확인.

## 효과가 있다 ≠ 검증·반복이 필요 없다 — 정직한 경계

두 논문 다 **"첫 시도 품질을 높인다"고만 주장**하지, "검증이나 반복이
필요 없어진다"고는 주장하지 않는다. 이 경계를 넘겨서 인용하면
그 자체가 [03-epistemic-immunity-catalog.md](03-epistemic-immunity-catalog.md)
2번(가짜 정밀함 — 근거가 실제로 뒷받침하는 것보다 더 강하게 주장하기)에
해당한다.

**실제 적용 사례(n=1, 통계적 근거 아님, 정직하게 명시)**: 이 프레임워크를
실제로 쓴 한 빌드에서, 기획서→설계 명세→평가 기준을 구현보다 먼저
확정하고 진행한 결과 **1회차 자동 검증에서 22개 기준 중 20개(91%)를
바로 통과**했다. 방향은 위 논문들의 패턴과 일치하지만, 이 사례 하나로
효과 크기를 일반화하지 않는다. 나머지 2개는 검증 스크립트 자체의 버그였고
— 즉 "명세를 먼저 썼다"는 게 버그를 아예 없애주진 않았고, 원인 진단과
수정에는 여전히 반복이 필요했다.

## 범위 경계 — 검증된 것과 추론뿐인 것을 섞지 않는다

🟢 위 두 논문이 실측한 범위: **단일 수학 문제 추론**, **단일 함수 규모
코드 생성**. 🟠 이 크리스탈이 놓인 맥락(기획서→설계→데이터→백엔드→
프론트엔드→평가로 이어지는 멀티파일 제품 빌드)까지 같은 효과 크기가
그대로 전이된다는 근거는 **없다** — 방향은 같을 가능성이 높다고
추론할 뿐, 검증된 사실로 과장하지 않는다. 규모가 커질수록 "계획"
자체의 복잡도도 커지므로, 오히려 계획 단계의 오류가 더 크게 증폭될
위험도 이론적으로는 있다(이 세션이 검증하지 않은 반대 가설 — 존재를
숨기지 않는다).

## 적용하는 법

1. 구현(코드)에 들어가기 전, **먼저 스펙 문서를 쓴다** — 프롬프트
   안에서만 계획을 세우는 게 아니라, 파일로 남겨서 다음 단계(구현,
   평가)가 그 파일을 참조하게 한다(단순 프롬프트 기법보다 한 단계 더
   강한 버전 — 사람도 나중에 다시 읽고 검증할 수 있다).
2. 스펙에는 최소 **무엇을 만들 것인가(기획)**와 **어떻게 판정할
   것인가(평가 기준)**를 분리해서 쓴다 — 하나로 합치면 확증 편향(원하는
   결과에 맞춰 기준을 사후에 짜맞추는 것)을 막는 효과가 줄어든다.
3. 스펙만 쓰고 실제 검증(4번 크리스탈)을 생략하지 않는다 — 이 크리스탈
   단독으로는 "첫 시도가 더 나아진다"만 보장하지, "결과가 맞다"를
   보장하지 않는다.
