# agent-ops-framework 설계도 — 무엇이며, 어떻게 자라나는가

> 🌐 **[Read in English](../en/BLUEPRINT.md)**

`README.md`가 "지금 무엇이 있는지"의 지도라면, 이 문서는 "**왜 이런
모양이고, 다음 크리스탈은 어떤 기준으로 들어오고, 그 편입이 어떻게
자동으로 발견되는가**"를 다룬다 — 어느 프로젝트든 자신의 전체 구조를
설명하는 프로젝트 설계도 문서를 두는 것처럼, 이 문서는 그 역할을 이
폴더 자신에 대해 한다.

## 1. 정체성 — 크리스탈이란 무엇인가

크리스탈은 **완결된 스펙이 아니라 살아있는 참조 프레임워크의 한 조각**이다.
세 가지가 항상 같이 있어야 크리스탈이다:

1. **도메인 무관 서술** — 특정 프로젝트의 고유명사·날짜·사용자 발언이
   없다. 원리와 절차만 남는다.
2. **검증 강도 표시** — 🟢(1차 자료 핵심 내용 직접 확인) 또는 🟡(골격·
   이름만 확인, 상세는 재구성)로 매 문서 서두에 명시된다. 표시 없는
   크리스탈은 존재할 수 없다 — 근거 없이 그럴듯한 원칙을 지어내는 건
   이 프레임워크가 막으려는 실패 패턴 그 자체([03-epistemic-immunity-
   catalog.md](03-epistemic-immunity-catalog.md))다.
3. **최소 1개 근거 경로** — (a) 어느 프로젝트의 실제 운영 이력에서 실전
   검증된 것을 서사만 걷어내고 패턴만 남겼거나, (b) 외부의 검증 가능한
   표준(논문·공식 사양·업계 프레임워크)의 핵심 주장을 원문 대조했거나,
   둘 중 하나다. 둘 다 아니면 크리스탈이 아니라 그냥 의견이다.
4. **버전+콘텐츠 해시 헤더** — 제목 바로 아래 `**버전**: <major>.<minor>.
   <patch>`와 `**콘텐츠 해시**: sha256:<본문 해시>`가 온다. 이건 이
   저장소의 git 이력에 기대지 않는, **크리스탈 파일 하나만 복사해도
   따라오는 버저닝**이다 — 세맨틱 버전은 변경의 성격(주요 원칙이
   바뀜/새 메커니즘 추가/표현만 수정)을 전달하고, 콘텐츠 해시는 그
   버전 번호가 실제로 지금 내용과 일치하는지 100% 기계적으로 검증한다.
   `agent-ops-framework-version-stamp.py`로 올리고
   `agent-ops-framework-version-check.py`로 검증한다(5절에 상세).

## 2. 편입 게이트 — "최고 수준의 퀄리티만 존재해야 한다"를 구체적 기준으로

새 크리스탈 후보가 실제로 편입되려면 아래 6개 게이트를 **전부** 통과해야
한다. 하나라도 못 넘으면 편입 보류(REFLECTION-CANDIDATES.md에 "반영
보류"로 이유와 함께 남긴다 — 조용히 버리지 않는다).

| # | 게이트 | 판정 방법 |
|---|---|---|
| G1 | 검증 강도가 매겨질 수 있는가 | 1차 자료를 최소 1번 실제로 열어봤는가(🟢), 아니면 골격만 확인하고 그렇게 명시할 것인가(🟡). 둘 다 안 되면 편입 불가 |
| G2 | 도메인 지식이 최소화됐는가 | 날짜·특정 프로젝트명·사용자 인용문을 뺐을 때도 문서가 온전히 성립하는가(위 1절 참고). `RISK-ANALYSIS.md`만 이 게이트의 명시적 예외다 |
| G3 | 기존 크리스탈과 실질적으로 겹치지 않는가 | 최소 1개 기존 크리스탈을 실제로 다시 읽고 대조한다(Chesterton's Fence — 왜 없었는지 먼저 확인 없이 새로 안 만든다) |
| G4 | 카테고리에 배치 가능한가 | 기존 9개 카테고리 중 하나에 들어가거나, 새 카테고리를 만들 만큼 충분히 다른 축인지 판단한다. 카테고리 하나가 6~7개를 넘으면 편입 전에 분할부터 검토한다(README.md "규모가 커질 때의 원칙") |
| G5 | 공개 안전성 | (원본 프로젝트 자신이 추출할 때) `RISK-ANALYSIS.md`의 4질문 결정 트리를 다시 대입해 원본 프로젝트의 기밀·경쟁 정보를 끌고 들어오지 않는지 확인한다. (외부 기여자가 자신의 다른 프로젝트·소속 조직 경험에서 크리스탈을 제안할 때) `RISK-ANALYSIS.md`는 원본 프로젝트에 특정된 문서라 그대로 못 쓴다 — 대신 [35-personal-oss-employer-confidentiality-separation.md](35-personal-oss-employer-confidentiality-separation.md)의 판단(콘텐츠 독자성 + 소속 관계상 허용 여부)을 자신의 상황에 적용한다. 두 경우 모두 **자동 스캐너([07-prompt-guardrails/](07-prompt-guardrails/))가 잡는 건 패턴 매칭 가능한 크리덴셜·개인정보뿐**이라, 핵심 영업정보·비공개 기술·전략처럼 패턴으로 못 잡는 기밀은 이 게이트에서 사람이 직접 판단해야 한다 |
| G6 | 사용법 문서 갱신 | `USAGE-GUIDE.md`에 "이런 상황이면 이 크리스탈"이 최소 1줄 추가될 수 있는가 — 못 채우면 아직 실전에서 언제 쓰는지가 불명확하다는 신호다 |

## 3. 성장 프로세스 — 발견부터 통합까지 4단계

```
1. 발견(discovery)   원본 프로젝트가 스스로 고도화하며 새 구조적 패턴을
                     만든다 — 사람이 알아차리거나, 아래 4절의 자동
                     스캐너가 후보로 플래그한다
        ↓
2. 검토(review)      위 2절 6개 게이트를 하나씩 대입. 통과/보류를
                     REFLECTION-CANDIDATES.md 상태 칸에 기록(조용히
                     넘어가지 않음)
        ↓
3. 추출(extraction)  서사를 걷어내고 원리·절차만 남긴 크리스탈 파일 작성,
                     검증 강도 표시, 다음 번호 부여
        ↓
4. 통합(integration) README.md 카테고리 표에 한 줄 추가, USAGE-GUIDE.md
                     갱신, 카테고리 크기 재확인(6~7개 넘으면 분할 검토)
```

## 4. 자동화 — "다른 프로젝트 고도화"를 놓치지 않고 발견하기

**문제**: 원본 프로젝트(또는 이 프레임워크를 가져다 쓰는 어떤 프로젝트든)가
계속 고도화되는데, 그 고도화 중 어느 게 이식 가능한 구조적 패턴인지는
사람이 매번 기억해서 되짚어보지 않으면 놓친다. "나중에 반영하자"고 문서에
적어두는 것만으로는 재발을 못 막는다는 게 이 프레임워크의 원본 프로젝트
자신이 이미 겪은 일이다([06-self-improving-heuristics-loop.md](06-self-improving-heuristics-loop.md)와
같은 문제의식).

**자동화된 부분(발견만)**: 지시·변경 이력을 훑어 "원칙/규칙/체계/기준/
가드레일/게이트/프레임워크/자동화" 같은 신호어가 있고 이 프레임워크
자신에 대한 이야기가 아닌 항목을, 이 프레임워크가 아닌 다른 프로젝트가
고도화될 때마다 자동으로 후보 목록에 추가한다. 후보 목록은 append-only다
— 검토되기 전엔 사라지지 않는다.

**정직한 한계 — 이 스캐너는 내부 이력만 본다(2026-09-01 레드팀 감사로
확인)**: 지금까지 이 프레임워크에 추가된 크리스탈 중 최소 1건(비용·예산
관리 축)은 자동 스캐너가 아니라 **사용자가 "이게 X 기준을 충족하나?"라고
직접 물어서** 발견됐다 — 스캐너는 원본 프로젝트 자신의 지시 이력만
훑지, agentops.ai류 외부 프레임워크와의 대조나 "우리가 놓치고 있는 축이
뭘까"류 능동적 벤치마킹은 하지 않는다. 이건 확인 편향(confirmation
bias)의 구조적 원인이 될 수 있다 — 질문받은 것만 확인하고, 스스로
찾아 나서는 축은 내부 이력 재탕에 머무를 위험. 아직 몇 건 안 되는
관측이라 이게 얼마나 만연한 패턴인지 단정하지 않지만, 다음 확장
후보로 남긴다: 외부 프레임워크 대조를 정기적으로 자동화할지.

**의도적으로 자동화하지 않은 부분(판단)**: 후보를 실제 크리스탈로
바꾸는 것(위 2절 게이트 통과 여부)은 자동화하지 않는다. 여기를 자동화하면
게이트 자체가 형식적 통과의례가 되고 "최고 수준의 퀄리티만"이라는 요구가
무너진다 — 발견(detection)과 실행(execution)을 분리하는 건 이 폴더에 이미
있는 원칙([04-eval-engineering-methodology.md](04-eval-engineering-methodology.md)의
자동 채점과 [13-debt-and-quality-bar.md](13-debt-and-quality-bar.md)의
부채 우선순위 판단이 똑같이 이 경계를 지킨다)이다.

**이식할 때 구현 형태**: 이 폴더를 가져다 쓰는 프로젝트는 `docs/
directive-registry.md`류(지시·변경을 번호로 누적하는 표)가 있다면 그걸
스캔 대상으로 삼고, 없다면 git 커밋 로그나 변경 이력 문서 아무거나
스캔 대상으로 바꿔 같은 4단계(발견→검토→추출→통합)를 그대로 적용할 수
있다 — 스캔 대상이 어떤 형식이든 "신호어 매칭 → 후보 누적 → 사람/AI
검토"라는 골격은 동일하다.

## 5. 버전·변경 관리

- 크리스탈 번호는 영구적이다 — 크리스탈을 폐기해도 번호를 재사용하지
  않는다(`02-directive-registry.md`가 이미 쓰는 "폐기됨" 원칙과 동일).
- 크리스탈 내용이 갱신되면(예: 검증 강도가 🟡에서 🟢로 올라가면) 파일을
  직접 고친다 — 이 폴더 안에는 "언제 왜 고쳤는지" 이력을 남기지 않는다
  (도메인 지식 최소화 원칙, 위 1절 G2). 그 이력은 이 폴더를 가져다 쓰는
  원본 프로젝트 쪽의 변경 이력 문서에 남는다.
- 카테고리를 쪼갤 땐 번호는 그대로 두고 README.md 표의 소속 카테고리만
  옮긴다 — 크리스탈을 참조하는 외부 링크(`NN-파일명.md`)가 깨지지
  않는다.

**크리스탈 내용을 실제로 고칠 때**(위 1절 G4의 버전+해시 헤더):
1. 내용을 고친다.
2. `./scripts/agent-ops-framework-version-stamp.py <파일> --bump=<major|
   minor|patch>`를 돌린다 — 어느 수준으로 올릴지는 매번 사람/AI가
   판단한다(자동 기본값 없음, 침묵하는 자동판단을 만들지 않는다):
   - `major`: 원칙 자체가 바뀌거나 뒤집힘(드묾).
   - `minor`: 새 메커니즘/절이 추가됨(원칙은 그대로, 범위만 넓어짐) —
     이 세션에서 05·09번에 절을 추가한 것들이 이 수준의 예시다.
   - `patch`: 표현·오타·링크 수정(의미 변화 없음).
3. `./scripts/agent-ops-framework-version-check.py`로 저장된 해시가
   실제 본문과 일치하는지 확인한다(git 이력 불필요, 100% 기계적).
4. `en/` 번역이 있으면 7절의 번역 동기화(STALE) 절차대로 갱신한다.

**왜 버전과 해시를 나눴는가**: 버전(세맨틱)은 사람에게 "이 변경이 얼마나
중요한지"를 전달하는 축이고, 해시(SHA-256, 이 저장소 git 이력과 무관하게
계산됨)는 "지금 이 파일이 헤더가 주장하는 그 버전과 실제로 일치하는가"를
기계적으로 검증하는 축이다 — 서로 다른 문제를 푼다. 해시만 있으면
사람이 "뭐가 얼마나 바뀌었는지" 알 방법이 없고, 버전만 있으면 사람이
깜빡하고 안 올려도 아무도 못 잡는다.

## 6. 이 문서 자체에도 같은 기준이 적용된다

이 문서는 크리스탈이 아니라 이 폴더의 거버넌스 문서지만(`RISK-ANALYSIS.md`와
같은 지위 — 크리스탈 목록 밖), G2(도메인 지식 최소화)는 이 문서에도 그대로
적용된다 — 날짜·특정 세션의 사용자 발언·특정 크리스탈 번호를 예시로 들지
않는다. 이 문서가 낡았다고 판단되는 조건은 [09-project-structure-
template.md](09-project-structure-template.md)의 "정합성 유지 규칙"과
같다: 게이트 기준이 실제로 바뀌거나, 성장 프로세스 단계 자체가 바뀌거나,
자동화 스캐너의 설계가 바뀔 때.

## 7. 새 프로젝트로 이식할 때 — 폴더 전체 복사 후 초기화할 것

이 폴더의 크리스탈 파일들(`NN-*.md`)은 그대로 복사해도 안전하다 — G2(도메인
지식 최소화)를 통과했기 때문이다. 하지만 **폴더 안의 운영용 상태 파일 두
개는 원본 프로젝트의 실행 이력을 담고 있어 그대로 들고 가면 안 된다**:

- **`REFLECTION-CANDIDATES.md`**: 원본 프로젝트의 directive-registry에서
  뽑힌 후보 행이 누적된 **작업 로그**다 — 크리스탈이 아니라 "무엇을
  검토했는지"의 이력이라, 새 프로젝트로 옮기면 그 자체가 도메인 지식(원본
  프로젝트의 특정 지시·판단 서사)이 된다. 새 프로젝트에서는 이 파일을
  헤더(스캐너 설명 + 빈 표)만 남기고 초기화한다.
- **`.reflection-checkpoint`**: "직전까지 어디까지 스캔했는지"를 원본
  프로젝트의 directive-registry 번호로 기록한 상태값이다 — 새 프로젝트는
  자기 자신의 directive-registry를 0부터 시작하므로 이 파일도 삭제하거나
  0으로 초기화한다.
- **스캐너 스크립트(`agent-ops-framework-reflection-check.py`,
  `agent-ops-framework-sync-check.py`, `agent-ops-framework-translation-
  sync-check.py`)의 경로 상수**는 그대로 유지해도 된다 — `docs/
  directive-registry.md`처럼 새 프로젝트도 같은 상대 경로(`agent-ops-
  framework/ko/`)에 자기 자신의 지시 레지스트리·크리스탈을 두는 걸
  전제로 설계됐다(이식 대상 프로젝트가 이 폴더 자체의 관행을 함께
  채택한다는 가정, [02](02-directive-registry.md) 참고). `ORIGIN_MAP`
  (sync-check용 원본↔크리스탈 매핑)은 원본 프로젝트의 파일 경로를 담고
  있어 **새 프로젝트 자신의 원본 문서 경로로 다시 채워야 한다** — 이것도
  도메인 지식이다.
- **`RISK-ANALYSIS.md`**: 이 문서 자체가 명시적 예외(위 1절)라 원본
  프로젝트의 실제 판단(콘텐츠 리스크 평가 등)이 남아있다 — 새 프로젝트는
  이 문서의 **틀(4개 질문 + 결정 트리)**만 재사용하고, 실제 답은 새
  프로젝트 자신의 상황으로 다시 채운다.
- **`DISCLAIMER.md`**: 위 셋과 달리 이 파일은 **그대로 복사해도 안전하다**
  — 빈칸(소속 조직명)만 채우면 되는 재사용 템플릿이라 원본 프로젝트의
  실행 이력을 담고 있지 않다(G2 통과). 초기화 대상이 아니라는 걸 이 표에
  명시해 둔다 — 위 셋과 똑같이 취급해 실수로 비워버리지 않게.

이 초기화를 빠뜨리면 새 프로젝트의 "도메인 무관 구조적 결정체"가 첫날부터
원본 프로젝트의 이력을 섞어 든 채로 시작하게 된다 — G2가 개별 크리스탈에는
지켜졌어도 폴더 전체 상태로는 깨지는 경우다.

**언어(SSOT는 한국어 버전에 고정)**: 이 폴더를 실제로 더 넓은 대상에게 공개할
때는 영문 번역이 필요해질 수 있다. 하지만 **폴더가 계속 활발히 자라는
동안(크리스탈이 계속 추가·수정·분할되는 지금 같은 시기)** 두 언어를
동시에 유지하면, 이 폴더 자신이 `sync-check.py`로 막으려는 것과 같은
종류의 드리프트(원본↔번역본이 갈라짐)가 구조적으로 생긴다 — 번역이 원문
수정마다 뒤따라가야 하는 유지비용이 계속 발생한다. **결정**: 번역은
상시 병행 유지가 아니라, 실제로 별도 저장소로 추출/공개하는 시점에
**1회성 스냅샷 작업**으로 한다 — 그 전까지는 이 문서(단일 소스)만
계속 고친다.

**번역 동기화는 `agent-ops-framework-translation-sync-check.py`가
양방향으로 감지한다.** 한 번 번역을 만든 뒤에도 SSOT는 계속 바뀐다 —
"번역본이 SSOT보다 뒤처졌는지"를 사람이 기억해서 확인하는 대신, `sync-
check.py`와 같은 설계(원본 문서의 최근 커밋을 대응 크리스탈과 비교)를
번역 파일에도 적용한다: 각 번역 파일에 "SSOT의 어느 커밋을 번역한
것인지"를 스탬프로 기록해두고, SSOT가 그 이후 바뀌면 스크립트가 두
종류의 신호 중 하나를 낸다(자동으로 재번역하지는 않는다 — 발견은
자동, 판단은 사람, BLUEPRINT 4절과 같은 원칙):

- **STALE(낡음)**: SSOT가 스탬프된 커밋 이후 바뀌었다 — 흔하고 저위험,
  그냥 최신 SSOT에서 다시 번역하고 스탬프를 갱신하면 된다.
- **DIVERGED(분기)**: 번역 파일 **자체**가 스탬프 갱신 없이 직접 수정된
  경우다 — 예를 들어 한국어를 못 읽는 기여자가 `en/NN.md`를 PR로 직접
  고친 경우가 정확히 이 신호를 만든다. **이건 STALE과 다르게 절대 그냥
  덮어쓰면 안 된다** — 번역 쪽에 실제 기여(오역 수정, 더 나은 설명, 새로
  발견한 결함)가 남아있는 상태이기 때문이다.

**진짜 양방향 흐름 — "번역본을 절대 고치지 않는다"에서 "고쳐도 되지만
반드시 SSOT로 되돌려 반영한다"로**: 이전 버전의 이 절은 번역본 직접
수정을 금지했다. 하지만 진짜 오픈소스가 되려면 한국어를 못 읽는
기여자도 실질적으로 기여할 수 있어야 한다 — 그들이 `en/`에 낸 PR을
"규칙 위반"으로 버리는 건 기여를 막는 것과 같다. 그래서 규칙을
바꾼다: **직접 수정은 허용하되, 그 수정이 SSOT로 반드시 되돌아가야
한다는 조율(reconciliation) 절차를 명시한다**:

1. DIVERGED 신호가 뜨면(위 스크립트), 그 변경 내용을 확인한다.
2. 그 변경이 실제로 유효하면(오역 수정, 개선 등), **SSOT(예: `ko/NN.md`)를
   먼저 고친다** — 번역 파일의 변경을 그대로 두고 넘어가지 않는다.
3. SSOT를 새로 커밋한 뒤, 그 커밋을 기준으로 번역 파일을 다시 번역하고
   스탬프를 그 새 커밋으로 갱신한다.
4. **왜 자동 병합을 안 하는가**: 산문(prose)은 코드처럼 3-way 병합이
   안전하지 않다 — 두 언어 버전이 각자 자연스럽게 다르게 표현될 수
   있어서, 기계적으로 병합하면 의미가 깨지기 쉽다. 그래서 이 메커니즘은
   "충돌을 자동으로 푸는 것"이 아니라 "충돌 가능성이 있는 지점을
   정확히 짚어서, 사람/AI가 매번 처음부터 두 버전을 통째로 비교하지
   않아도 되게" 하는 것까지가 역할이다.

**드물게 특정 파일 하나의 SSOT를 뒤집을 수도 있다**: 예를 들어 어떤
크리스탈이 애초에 영어권 기여자의 독자 연구에서 출발했다면, 그 파일
하나만 `en/`이 SSOT가 되고 `ko/`가 번역이 되는 것도 허용한다 — 스탬프를
반대쪽 파일에 붙이면 된다(어느 쪽에 스탬프가 있는지가 곧 "이 파일은
번역"이라는 뜻이고, 스탬프가 없는 쪽이 SSOT다 — `translation-sync-
check.py`가 이 방향을 자동으로 인식한다). 이건 예외이지 기본값이
아니다 — 기본값은 여전히 한국어가 SSOT다.

**AI가 어느 언어를 읽을지는 별도 설정 파일로 뺐다**: 이 문서(BLUEPRINT.md)는
"왜 SSOT가 한국어이고 번역을 어떻게 관리하는가"라는 **정책·근거**를
다룬다. "이 프레임워크를 읽는 AI가 지금 이 순간 실제로 어느 파일을 열지"는
매번 판단하는 게 아니라 [LANGUAGE-POLICY.md](LANGUAGE-POLICY.md)에 기본값과
티어·예외로 명시해뒀다 — 근거 문서와 실행 시점 설정을 분리한 이유는 이
문서 4절이 이미 짚은 "문서에 적어두는 것만으로는 재발을 못 막는다"는
교훈과 같은 정신이다: 정책을 읽고 매번 다시 추론하게 하는 것보다, 바로
참조할 수 있는 결정 규칙을 둔다.
